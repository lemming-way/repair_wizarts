# Приложение № 1

# Спецификация формата статей Repair Wizards для внешних ИИ

**Версия документа:** 1.3  
**Версия формата данных:** 1.3

## 1. Назначение

Документ определяет единый формат подготовки и передачи статей в Repair Wizards с использованием любых внешних ИИ и инструментов создания контента.

Формат предназначен прежде всего для публикации материалов по ремонту и обслуживанию бытовой электроники и приборов:

- смартфонов и планшетов;
- персональных компьютеров и ноутбуков;
- телевизоров и мониторов;
- бытовой техники;
- электронных плат и компонентов;
- периферийных устройств;
- других электронных и электротехнических приборов.

Формат также допускает публикацию материалов по ремонту других объектов и оборудования, а также обычных информационных и обучающих статей.

Статья может содержать не только материал для чтения человеком, но и структурированные технические знания, предназначенные для последующего машинного использования: подготовки диагностических брифов, уточнения требований заказчика, формирования технического задания и помощи мастеру.

## 2. Разделение ответственности

### 2.1. Внешний ИИ или инструмент подготовки контента

Внешний инструмент выполняет:

- подготовку текста;
- структурирование статьи на блоки;
- создание пошаговых инструкций;
- подготовку технических таблиц;
- подготовку команд и фрагментов кода;
- подбор или создание иллюстраций;
- подготовку галерей;
- подбор видеоматериалов;
- подготовку 3D-моделей, если это необходимо и возможно;
- подготовку структурированных технических знаний, если они применимы к статье;
- формирование `article.json`;
- комплектацию файлов в ZIP-архив.

Внешний ИИ не обязан самостоятельно создавать сложные технические схемы и 3D-модели. Он может использовать файлы, предоставленные мастером, или материалы, подготовленные специализированными инструментами.

Внешний ИИ должен отделять наблюдаемые факты от предположений и не должен выдавать неподтверждённые диагностические выводы за установленную неисправность.

### 2.2. Repair Wizards

Repair Wizards отвечает за:

- приём ZIP-архива;
- проверку структуры и содержимого;
- проверку JSON;
- проверку файлов и связей между ними;
- хранение статьи и медиафайлов;
- предварительный просмотр;
- согласование и публикацию.

Repair Wizards не содержит встроенного редактора статей и не зависит от API конкретного ИИ.

В рамках версии 1.3 Repair Wizards принимает, проверяет, хранит и выдаёт структурированные технические данные. Выполнение диагностических сценариев, интерпретация ответов заказчика и автоматическое формирование заказов в эту версию не входят.

## 3. Формат передачи

Статья передаётся в ZIP-архиве:

```text
article.zip
├── article.json
└── media/
    ├── cover.jpg
    ├── image_001.webp
    ├── image_002.jpg
    ├── step_01.jpg
    ├── repair_model.glb
    └── model_texture.png
```

Корень архива содержит `article.json` и каталог `media/`.

В каталоге `media/` хранятся все изображения, 3D-модели и необходимые зависимости моделей.

Предпочтительный формат 3D-моделей — GLB. Формат glTF допускается при условии включения всех внешних зависимостей в архив.

## 4. Структура article.json

Пример минимальной статьи:

```json
{
  "format_version": "1.3",
  "title": "Замена аккумулятора смартфона",
  "summary": "Пошаговая инструкция по замене аккумулятора.",
  "topic": {
    "name": "Ремонт смартфонов",
    "path": [
      "Электроника",
      "Смартфоны",
      "Ремонт"
    ]
  },
  "cover": {
    "file": "media/cover.jpg",
    "alt": "Смартфон с открытой задней крышкой"
  },
  "assets": [
    {
      "file": "media/cover.jpg",
      "type": "image",
      "format": "jpg",
      "size_bytes": 245000
    },
    {
      "file": "media/step_01.jpg",
      "type": "image",
      "format": "jpg",
      "size_bytes": 310000
    }
  ],
  "blocks": [
    {
      "type": "heading",
      "level": 2,
      "text": "Подготовка"
    },
    {
      "type": "paragraph",
      "text": "Перед началом работы выключите устройство."
    }
  ]
}
```

В версии 1.3 допускается дополнительное корневое поле `technical_knowledge`. Оно предназначено для структурированных технических данных и не является обязательным.

### 4.1. Корневые поля

| Поле | Тип | Обязательность |
|---|---|---|
| `format_version` | string | Да |
| `title` | string | Да |
| `summary` | string | Да |
| `topic` | object | Да |
| `cover` | object | Нет |
| `assets` | array | Да |
| `blocks` | array | Да |
| `technical_knowledge` | object | Нет |

Отсутствие `technical_knowledge` не является ошибкой. Обычная информационная статья может состоять только из стандартных полей и `blocks`.

### 4.2. Тематическая классификация

Объект `topic` содержит:

- `name` — предлагаемое название темы;
- `path` — массив названий от родительской темы к дочерней.

Внешний ИИ не назначает идентификаторы тем. Repair Wizards сопоставляет предложенную тему с существующей иерархией `blog_topic`.

### 4.3. Обложка

Объект `cover` содержит:

- `file` — путь к изображению;
- `alt` — описание изображения.

Файл обложки обязательно регистрируется в `assets`.

## 5. Реестр файлов assets

`assets` содержит перечень всех файлов, используемых статьёй, включая файлы, на которые ссылаются обычные блоки и структурированные технические данные.

Поля элемента:

| Поле | Тип | Обязательность |
|---|---|---|
| `file` | string | Да |
| `type` | string | Да |
| `format` | string | Да |
| `size_bytes` | integer | Да |

Допустимые значения `type`:

- `image`;
- `model_3d`.

Каждый файл указывается в `assets` один раз.

Все ссылки на файлы из `cover`, `blocks` и `technical_knowledge` должны соответствовать записям в `assets`.

### 5.1. Серверные метаданные хранения

При подготовке ZIP внешний автор передаёт только поля формата (`file`, `type`, `format`, `size_bytes`). Сервер после импорта может добавить к элементу `assets` поле `dl_id` — числовой идентификатор файла в существующем Dropbox-хранилище Repair Wizards. Это внутреннее серверное поле: его нельзя задавать во входном ZIP или использовать как логический путь файла.

Исходное значение `file` сохраняется без замены. Ссылки в `cover`, `blocks` и `technical_knowledge` продолжают указывать на этот путь; клиент разрешает его через соответствующий элемент `assets` и получает `dl_id`. Таким образом, один файл может использоваться в нескольких местах статьи без повторной загрузки.

Для старых статей без `dl_id` сохраняется поддержка прежнего разрешения медиа-ссылок. Подробный механизм хранения и выдачи описан в Приложении № 3 — `repair-wizards-article-dropbox-storage-contract-v1.3.md`.

Один и тот же зарегистрированный файл может использоваться в нескольких местах статьи и в нескольких технических сущностях. Повторная регистрация файла в `assets` не допускается.

Система проверяет наличие файлов, их фактический размер, формат и использование в статье.

Видеоматериалы передаются по внешним ссылкам и не включаются в ZIP.

## 6. Поддерживаемые типы блоков

Блоки располагаются в массиве `blocks` в порядке отображения статьи. В версии 1.3 сохраняются все типы блоков версии 1.2 без изменения их назначения и структуры.

### 6.1. Заголовок — heading

```json
{
  "type": "heading",
  "level": 2,
  "text": "Название раздела"
}
```

`level` — от 2 до 4. Заголовок первого уровня используется для названия статьи.

### 6.2. Текстовый абзац — paragraph

```json
{
  "type": "paragraph",
  "text": "Текст абзаца."
}
```

Обычный текст без произвольной HTML-разметки.

### 6.3. Изображение — image

```json
{
  "type": "image",
  "file": "media/image_001.webp",
  "caption": "Подпись к изображению",
  "alt": "Описание изображения"
}
```

Файл должен быть зарегистрирован в `assets`.

### 6.4. Галерея — gallery

```json
{
  "type": "gallery",
  "images": [
    {
      "file": "media/image_001.webp",
      "caption": "Первый этап",
      "alt": "Описание первого изображения"
    },
    {
      "file": "media/image_002.jpg",
      "caption": "Второй этап",
      "alt": "Описание второго изображения"
    }
  ]
}
```

Минимальное количество изображений — 2.

Отображение:

- горизонтальная прокрутка;
- свайп на мобильных устройствах;
- стрелки навигации на настольных устройствах;
- увеличение изображения;
- подписи;
- адаптация к экрану.

### 6.5. Видео — video

```json
{
  "type": "video",
  "url": "https://www.youtube.com/watch?v=example",
  "caption": "Демонстрация ремонта"
}
```

Допускаются только поддерживаемые Repair Wizards видеоплатформы.

Произвольный HTML-код плеера не допускается.

### 6.6. Список — list

```json
{
  "type": "list",
  "style": "ordered",
  "items": [
    "Первый шаг",
    "Второй шаг",
    "Третий шаг"
  ]
}
```

`style` принимает значения `ordered` или `unordered`.

### 6.7. Цитата — quote

```json
{
  "type": "quote",
  "text": "Текст цитаты",
  "caption": "Источник или автор"
}
```

`caption` необязателен.

### 6.8. Информационный блок — callout

```json
{
  "type": "callout",
  "style": "warning",
  "title": "Внимание",
  "text": "Перед началом работы отключите устройство от электросети."
}
```

Допустимые значения `style`:

- `info`;
- `warning`;
- `danger`;
- `tip`.

`title` необязателен.

### 6.9. Пошаговая инструкция — steps

Блок предназначен для описания последовательности ремонтных действий с привязкой фотографий и предупреждений к конкретным шагам.

```json
{
  "type": "steps",
  "items": [
    {
      "title": "Снять заднюю крышку",
      "text": "Прогреть края крышки и аккуратно отделить её от корпуса.",
      "image": "media/step_01.jpg",
      "warning": "Не повредите шлейф сканера отпечатка."
    },
    {
      "title": "Отключить аккумулятор",
      "text": "Отсоединить разъём аккумулятора от системной платы.",
      "image": "media/step_02.jpg"
    }
  ]
}
```

Поля каждого шага:

| Поле | Тип | Обязательность |
|---|---|---|
| `title` | string | Да |
| `text` | string | Да |
| `image` | string | Нет |
| `warning` | string | Нет |

Изображение шага должно быть зарегистрировано в `assets`.

Отображение:

- последовательная нумерация;
- заголовок шага;
- текст инструкции;
- изображение, если оно задано;
- предупреждение, если оно задано.

Шаги отображаются в заданном порядке. Система не должна самостоятельно менять их последовательность.

### 6.10. Техническая таблица — table

Блок предназначен для справочных и сравнительных технических данных.

```json
{
  "type": "table",
  "headers": [
    "Контрольная точка",
    "Нормальное значение"
  ],
  "rows": [
    ["VBAT", "3.7–4.2 V"],
    ["USB VBUS", "5 V"],
    ["GND", "0 V"]
  ]
}
```

Поля:

- `type` — `table`;
- `headers` — массив заголовков колонок;
- `rows` — массив строк, каждая из которых содержит значения в соответствии с заголовками.

Требования:

- количество значений в каждой строке должно совпадать с количеством заголовков;
- значения передаются как текст;
- пустые значения допускаются;
- произвольный HTML не допускается.

Отображение:

- таблица с заголовками;
- адаптация к ширине экрана;
- горизонтальная прокрутка на узких экранах при необходимости;
- сохранение читаемости технических значений.

### 6.11. Код и команды — code

Блок предназначен для отображения команд, программного кода и диагностических инструкций.

```json
{
  "type": "code",
  "language": "bash",
  "text": "adb devices\nadb reboot bootloader"
}
```

Поля:

- `type` — `code`;
- `language` — язык или тип содержимого;
- `text` — текст кода или команд.

Возможные значения `language` могут включать:

- `bash`;
- `shell`;
- `powershell`;
- `cmd`;
- `sql`;
- `php`;
- `javascript`;
- `typescript`;
- `python`;
- `json`;
- `text`.

Допускается расширение списка языков без изменения структуры блока.

Отображение:

- моноширинный шрифт;
- сохранение форматирования и переносов строк;
- горизонтальная прокрутка длинных строк;
- возможность копирования содержимого.

Код и команды являются исключительно отображаемым текстом. Выполнение команд непосредственно из статьи не предусматривается.

### 6.12. 3D-модель — model_3d

Блок предназначен для интерактивного просмотра модели непосредственно в статье.

```json
{
  "type": "model_3d",
  "file": "media/repair_model.glb",
  "caption": "Модель узла устройства",
  "alt": "Трёхмерная модель узла в сборе",
  "controls": {
    "rotate": true,
    "zoom": true,
    "pan": false
  },
  "camera": {
    "azimuth": 45,
    "elevation": 70
  },
  "scale": 1
}
```

Поля:

| Поле | Тип | Обязательность |
|---|---|---|
| `type` | string | Да |
| `file` | string | Да |
| `caption` | string | Нет |
| `alt` | string | Да |
| `controls` | object | Нет |
| `camera` | object | Нет |
| `scale` | number | Нет |

`controls`:

- `rotate` — вращение;
- `zoom` — масштабирование;
- `pan` — перемещение модели.

`camera`:

- `azimuth` — горизонтальный угол в градусах;
- `elevation` — вертикальный угол в градусах.

`scale` — начальный масштаб модели.

Поддерживаемые форматы:

- GLB;
- glTF.

Для glTF все внешние зависимости должны находиться внутри архива и быть перечислены в `assets`.

Предпочтителен GLB как самодостаточный файл.

## 7. Будущие типы блоков

Следующие возможности не входят в формат 1.3 как поддерживаемые типы блоков:

- `exploded_view` — разнесённая модель;
- `interactive_diagram` — интерактивная схема;
- `cad_model` — CAD-модель;
- `external_viewer` — специализированный внешний просмотрщик;
- `ar_model` — модель дополненной реальности.

Внешний ИИ не должен включать эти типы в `blocks`, пока соответствующая поддержка не будет реализована в Repair Wizards.

## 8. Требования к содержанию

Статья должна быть логически структурирована и ориентирована на практическое применение.

Для ремонтных материалов необходимо:

- отделять диагностику неисправности от процесса ремонта;
- указывать необходимые инструменты и материалы;
- приводить последовательность действий;
- отмечать опасные операции;
- указывать условия, при которых работу следует прекратить;
- приводить технические значения с единицами измерения;
- отличать подтверждённые данные от предположений.

Для сложных операций предпочтительно использовать `steps`, а не один длинный текстовый абзац.

Для технических параметров предпочтительно использовать `table`.

Для команд диагностики и программных фрагментов предпочтительно использовать `code`.

Если статья содержит `technical_knowledge`, дополнительно необходимо:

- отделять наблюдаемые симптомы от предполагаемых причин;
- указывать, кем может выполняться диагностическое действие: заказчиком, специалистом или любым из них;
- обозначать уровень риска;
- указывать необходимые инструменты;
- описывать возможные результаты проверки;
- задавать переходы между диагностическими шагами только через декларативные условия;
- указывать, какие операции требуют профессиональной квалификации;
- связывать опасности с конкретными диагностическими или ремонтными действиями;
- не превращать возможную причину в подтверждённый диагноз без соответствующих результатов проверки.

## 9. Достоверность технических материалов

Внешний ИИ не должен выдавать предположительные технические сведения за подтверждённые.

Особенно важно:

- не придумывать напряжения, сопротивления и номиналы;
- не выдавать приблизительные схемы за реальные схемы конкретной модели;
- не представлять условную 3D-модель как точную инженерную модель;
- не утверждать совместимость деталей без подтверждения;
- не предлагать опасные операции без соответствующих предупреждений;
- не обозначать причину неисправности как подтверждённую только на основании одного симптома;
- не предлагать заказчику самостоятельные действия, требующие профессиональной квалификации или создающие недопустимый риск.

Если точность модели, схемы или технического параметра не подтверждена, это должно быть явно указано в статье.

Значение `certainty = confirmed` для причины неисправности допустимо только при наличии подтверждающих диагностических данных. В противном случае следует использовать `possible` или `unverified`.

## 10. Ограничения файлов

| Параметр | Ограничение |
|---|---:|
| Максимальный размер ZIP | 100 MB |
| Максимальный размер изображения | 10 MB |
| Максимальный размер одной 3D-модели | 30 MB |
| Максимальный суммарный размер модели glTF с зависимостями | 30 MB |
| Максимальное количество блоков в `blocks` | 200 |
| Минимальное количество изображений в галерее | 2 |
| Максимальная глубина каталогов | 2 |

Форматы изображений:

- JPG;
- JPEG;
- PNG;
- WebP.

Форматы 3D-моделей:

- GLB;
- glTF.

Количество технических сущностей в `technical_knowledge` не учитывается в лимите блоков `blocks`. Для защиты от чрезмерного объёма данных Backend применяет отдельные технические ограничения, согласованные с Приложением № 2.

## 11. Импорт

В интерфейсе автора предусматривается действие «Импортировать статью из файла».

Последовательность:

1. Автор выбирает ZIP-архив.
2. Система проверяет структуру архива.
3. Проверяется `article.json`.
4. Проверяются блоки и файлы.
5. Проверяются связи с `assets`.
6. Проверяются видеоссылки и 3D-модели.
7. Если присутствует `technical_knowledge`, проверяются его структура и связи.
8. Автор получает результат проверки.
9. При отсутствии ошибок доступен Preview.
10. Автор подтверждает импорт.
11. Статья сохраняется со статусом `draft`.

Ошибки должны указывать конкретное поле, блок, техническую сущность или файл.

Импорт не должен приводить к частичному сохранению статьи.

## 12. Предварительный просмотр

Preview должен использовать тот же механизм отображения, что и опубликованная статья.

Должны корректно отображаться все типы блоков версии 1.3:

- heading;
- paragraph;
- image;
- gallery;
- video;
- list;
- quote;
- callout;
- steps;
- table;
- code;
- model_3d.

Объект `technical_knowledge` не отображается как обычный текст или отдельный блок статьи. В версии 1.3 он сохраняется для последующего машинного использования.

Если ресурс не загружается, система должна показывать понятное сообщение, а не пустую область.

## 13. Версионирование и совместимость

Текущая версия формата — `1.3`.

Поле `format_version` обязательно.

Формат 1.3 сохраняет структуру и назначение всех блоков версии 1.2. Основное расширение — необязательный корневой объект `technical_knowledge`.

Требования:

- статьи версии 1.2 продолжают приниматься по правилам версии 1.2;
- статьи версии 1.3 принимаются как с `technical_knowledge`, так и без него;
- отсутствие `technical_knowledge` не является ошибкой;
- неизвестный тип блока приводит к ошибке импорта;
- неизвестные дополнительные поля не должны приводить к отказу обработки, если они не нарушают безопасность и корректность известных полей;
- неизвестные дополнительные поля должны сохраняться в исходном JSON без потери, даже если текущая версия Repair Wizards их не использует;
- произвольные HTML, JavaScript и исполняемый код не допускаются.

Наличие неизвестного дополнительного поля не означает, что Backend должен выполнять его содержимое или интерпретировать его как инструкцию.

## 14. Безопасность

Система должна:

- защищаться от ZIP Slip;
- запрещать абсолютные пути и выход за пределы каталога импорта;
- проверять реальные MIME-типы;
- проверять расширения и содержимое файлов;
- запрещать исполняемые файлы;
- ограничивать размеры распакованных данных;
- проверять внешние видеоссылки по разрешённому списку;
- исключать произвольную загрузку внешних ресурсов 3D-моделями;
- удалять временные файлы;
- выполнять импорт только для авторизованного пользователя.

Произвольные HTML, JavaScript и исполняемые выражения в технических данных не допускаются.

Условия диагностических переходов являются декларативными данными, а не программным кодом. Backend не выполняет код или выражения, переданные во внешнем JSON.

Код из блока `code` никогда не исполняется.

## 15. Интерфейс автора

Интерфейс импорта содержит:

- выбор ZIP-файла;
- результат проверки;
- список ошибок и предупреждений;
- предварительный просмотр;
- отмену;
- подтверждение импорта.

Встроенный редактор содержимого не предусматривается.

Для изменения содержимого автор подготавливает новый ZIP-архив и повторяет импорт либо использует предусмотренные системой функции управления статьёй.

## 16. Критерии приёмки формата

Формат считается реализованным, если:

1. Внешний инструмент может сформировать ZIP с `article.json` и `media/`.
2. Repair Wizards принимает корректный архив версии 1.3.
3. Система проверяет структуру JSON и `assets`.
4. Все ссылки на файлы проверяются.
5. Поддерживаются все типы блоков версии 1.2 без изменения их назначения.
6. Пошаговые инструкции отображаются с привязанными изображениями и предупреждениями.
7. Технические таблицы отображаются корректно на мобильных устройствах.
8. Код и команды отображаются с сохранением форматирования и возможностью копирования.
9. GLB/glTF-модели отображаются интерактивно.
10. Preview и опубликованная статья используют одинаковый механизм отображения.
11. Некорректные архивы и неизвестные типы блоков отклоняются.
12. Импорт не допускает выполнения произвольного кода.
13. При ошибке не сохраняется частично импортированная статья.
14. Корректные статьи версии 1.2 продолжают приниматься.
15. Статья версии 1.3 без `technical_knowledge` принимается.
16. Статья версии 1.3 с `technical_knowledge` принимается при корректной структуре и связях.
17. Структурированные технические данные могут ссылаться на файлы из общего `assets` без повторной регистрации файлов.
18. Неизвестные дополнительные поля сохраняются без потери.

## 17. Ограничения версии 1.3

# 18. Структурированные технические знания — technical_knowledge

## 18.1. Назначение

Корневой объект `technical_knowledge` предназначен для представления технической информации в форме, пригодной для машинной обработки.

Он может использоваться в будущем для:

- поиска технической информации по описанию проблемы;
- сопоставления симптомов и возможных причин;
- подготовки предварительного диагностического брифа для заказчика;
- определения необходимых инструментов и измерений;
- формирования предварительного технического задания для мастера;
- предоставления мастеру справочной информации по ремонту.

В версии 1.3 Repair Wizards только принимает, проверяет и сохраняет этот объект. Его выполнение или интерпретация в пользовательском интерфейсе не реализуются.

## 18.2. Общая структура

```json
{
  "technical_knowledge": {
    "schema_version": "1.0",
    "objects": [],
    "symptoms": [],
    "causes": [],
    "diagnostics": [],
    "operations": [],
    "tools": [],
    "materials": [],
    "safety": []
  }
}
```

`schema_version` обозначает версию структуры объекта `technical_knowledge` и не заменяет корневое поле `format_version`.

Все массивы внутри `technical_knowledge` необязательны. Допускается передавать только те массивы, которые применимы к конкретной статье.

Идентификаторы технических сущностей уникальны в пределах соответствующего массива. Для ссылок между сущностями используются их строковые идентификаторы.

## 18.3. Объекты ремонта — objects

Описывают устройства, оборудование, компоненты и узлы.

Пример:

```json
{
  "id": "OBJ001",
  "category": "smartphone",
  "name": "Смартфон",
  "manufacturer": "Samsung",
  "model": "Galaxy A52",
  "model_scope": "exact"
}
```

Поля:

| Поле | Тип | Обязательность |
|---|---|---|
| `id` | string | Да |
| `category` | string | Да |
| `name` | string | Да |
| `manufacturer` | string | Нет |
| `model` | string | Нет |
| `model_scope` | string | Нет |
| `parent_object_id` | string | Нет |
| `description` | string | Нет |

Допустимые значения `model_scope`:

- `exact` — конкретная модель;
- `model_family` — семейство моделей;
- `generic` — обобщённый тип оборудования.

`parent_object_id` используется для связи узла или компонента с родительским объектом и должен ссылаться на существующий объект в массиве `objects`.

## 18.4. Симптомы — symptoms

Описывают наблюдаемые проявления неисправностей.

Пример:

```json
{
  "id": "SYM001",
  "object_ids": ["OBJ001"],
  "title": "Не заряжается аккумулятор",
  "description": "При подключении зарядного устройства заряд не увеличивается"
}
```

Поля:

| Поле | Тип | Обязательность |
|---|---|---|
| `id` | string | Да |
| `object_ids` | array of string | Да |
| `title` | string | Да |
| `description` | string | Да |
| `media_refs` | array | Нет |

Симптом описывает наблюдение заказчика или специалиста и не должен автоматически считаться подтверждением конкретной неисправности.

## 18.5. Возможные причины — causes

Описывают причины, которые могут объяснять наблюдаемые симптомы.

Пример:

```json
{
  "id": "CAUSE001",
  "symptom_ids": ["SYM001"],
  "description": "Неисправность разъёма зарядки",
  "certainty": "possible"
}
```

Поля:

| Поле | Тип | Обязательность |
|---|---|---|
| `id` | string | Да |
| `symptom_ids` | array of string | Да |
| `description` | string | Да |
| `certainty` | string | Да |
| `diagnostic_refs` | array of string | Нет |

Допустимые значения `certainty`:

- `confirmed` — подтверждённая причина;
- `possible` — возможная причина;
- `unverified` — неподтверждённая гипотеза.

Значение `confirmed` допустимо только при наличии подтверждающих диагностических данных. Если подтверждение отсутствует, следует использовать `possible` или `unverified`.

## 18.6. Диагностические процедуры — diagnostics

Описывают последовательность проверок, позволяющих уточнить характер неисправности.

Пример:

```json
{
  "id": "DIAG001",
  "title": "Первичная проверка зарядки",
  "purpose": "Определить наличие реакции устройства на зарядное устройство",
  "performer": "customer",
  "risk_level": "low",
  "required_tool_ids": [],
  "steps": [
    {
      "id": "D001",
      "title": "Подключение зарядного устройства",
      "instruction": "Подключите штатное зарядное устройство",
      "method": "visual_check",
      "response": {
        "type": "choice",
        "options": [
          {"value": "yes", "label": "Индикатор загорелся"},
          {"value": "no", "label": "Индикатор не загорелся"}
        ]
      },
      "transitions": [
        {
          "operator": "eq",
          "value": "yes",
          "next_step_id": "D002"
        },
        {
          "operator": "eq",
          "value": "no",
          "next_step_id": "D003"
        }
      ]
    },
    {
      "id": "D002",
      "title": "Проверка зарядки",
      "instruction": "Проверьте изменение уровня заряда",
      "method": "observation",
      "response": {
        "type": "boolean"
      },
      "terminal": true
    },
    {
      "id": "D003",
      "title": "Прекращение пользовательской проверки",
      "instruction": "Передайте устройство специалисту",
      "method": "professional_inspection",
      "response": {
        "type": "text"
      },
      "terminal": true
    }
  ]
}
```

Поля диагностической процедуры:

| Поле | Тип | Обязательность |
|---|---|---|
| `id` | string | Да |
| `title` | string | Да |
| `purpose` | string | Да |
| `performer` | string | Да |
| `risk_level` | string | Да |
| `required_tool_ids` | array of string | Да |
| `steps` | array | Да |

Допустимые значения `performer`:

- `customer` — заказчик;
- `professional` — специалист;
- `either` — заказчик или специалист с учётом ограничений безопасности.

Допустимые значения `risk_level`:

- `low`;
- `medium`;
- `high`;
- `prohibited_for_customer`.

Допустимые методы диагностики:

- `question`;
- `visual_check`;
- `observation`;
- `measurement`;
- `functional_test`;
- `professional_inspection`.

Поля диагностического шага:

| Поле | Тип | Обязательность |
|---|---|---|
| `id` | string | Да |
| `title` | string | Да |
| `instruction` | string | Да |
| `method` | string | Да |
| `response` | object | Нет |
| `transitions` | array | Нет |
| `terminal` | boolean | Нет |
| `media_refs` | array | Нет |
| `safety_refs` | array of string | Нет |

`response` описывает тип ожидаемого результата. Поддерживаются:

- `choice` — выбор одного из предложенных вариантов; объект должен содержать `options`, каждый вариант — `value` и `label`;
- `boolean` — ответ да/нет;
- `text` — текстовый ответ;
- `number` — числовой ответ; при необходимости указываются `unit`, `min` и `max`;
- `image` — изображение;
- `video` — видеоматериал.

Для `number` поля `unit`, `min` и `max` необязательны. Если они указаны, `min` и `max` должны быть числами, а `min` не должен превышать `max`.

`transitions` описывает возможные переходы к следующим шагам. Каждый переход содержит:

- `operator` — оператор сравнения;
- `value` — значение для сравнения;
- `next_step_id` — идентификатор следующего шага.

Допустимые операторы:

- `eq` — равно;
- `ne` — не равно;
- `gt` — больше;
- `gte` — больше или равно;
- `lt` — меньше;
- `lte` — меньше или равно.

Переходы являются декларативными данными. Произвольные выражения, функции, скрипты и исполняемый код не допускаются.

`terminal = true` обозначает завершающий шаг процедуры. Для завершающего шага переходы не требуются.

Если шаг не является завершающим, для него должны быть описаны переходы или иным однозначным образом определено продолжение процедуры. Переходы должны ссылаться на существующие шаги той же диагностической процедуры.

Для числовых измерений должны быть указаны единицы измерения, если без них значение неоднозначно.

## 18.7. Ремонтные операции — operations


Поля:

| Поле | Тип | Обязательность |
|---|---|---|

| `performer` | string | Да |

| `tool_refs` | array of string | Нет |
| `material_refs` | array of string | Нет |
| `safety_refs` | array of string | Нет |
| `media_refs` | array | Нет |

Допустимые значения `performer`:

Допустимые значения `required_skill`:

Операция описывает возможный вид работ и не означает, что неисправность уже подтверждена или что именно эта операция обязательно потребуется.

## 18.8. Инструменты — tools

Описывают оборудование, необходимое для диагностики или ремонта.

Пример:

```json
{
  "id": "TOOL001",
  "name": "Цифровой мультиметр",
  "purpose": "Измерение напряжения",
  "access_options": [
    "customer_owned",
    "rentable",
    "professional_only"
  ],
  "specification": "Измерение постоянного напряжения"
}
```

Поля:

| Поле | Тип | Обязательность |
|---|---|---|
| `id` | string | Да |
| `name` | string | Да |
| `purpose` | string | Нет |
| `access_options` | array of string | Да |
| `specification` | string | Нет |
| `media_refs` | array | Нет |

Допустимые значения `access_options`:

- `customer_owned` — собственный инструмент заказчика;
- `rentable` — потенциально доступен в аренду;

Указание `rentable` означает только возможность использования арендуемого инструмента. Оно не означает наличие соответствующего предложения на бирже.

## 18.9. Материалы — materials

Описывают запчасти и расходные материалы.

Пример:

```json
{
  "id": "MAT001",
  "name": "Разъём зарядки",
  "purpose": "Замена неисправного компонента",
  "compatibility": "Требуется проверка совместимости с конкретной моделью"
}
```

Поля:

| Поле | Тип | Обязательность |
|---|---|---|
| `id` | string | Да |
| `name` | string | Да |
| `purpose` | string | Нет |
| `compatibility` | string | Нет |
| `media_refs` | array | Нет |

ИИ не должен самостоятельно утверждать совместимость детали без подтверждённых данных.

## 18.10. Требования безопасности — safety

Описывают ограничения, предупреждения и условия прекращения работ.

Пример:

```json
{
  "id": "SAFE001",
  "severity": "danger",
  "instruction": "Перед ремонтом отключить устройство от источника питания",
  "applies_to": ["DIAG001", "OP001"],
  "customer_allowed": false
}
```

Поля:

| Поле | Тип | Обязательность |
|---|---|---|
| `id` | string | Да |
| `severity` | string | Да |
| `instruction` | string | Да |
| `applies_to` | array of string | Нет |
| `customer_allowed` | boolean | Нет |

Допустимые значения `severity`:

- `info`;
- `warning`;
- `danger`.

`applies_to` содержит идентификаторы диагностических процедур и/или ремонтных операций, к которым относится предупреждение.

`customer_allowed = false` означает, что соответствующее действие не должно предлагаться заказчику для самостоятельного выполнения.

## 18.11. Привязка мультимедиа — media_refs

Структурированные технические данные могут ссылаться на файлы из общего реестра `assets`.

Пример:

```json
{
  "file": "media/step_01.jpg",
  "role": "operation",
  "caption": "Демонтаж разъёма",
  "alt": "Разъём зарядки на плате"
}
```

Поля:

| Поле | Тип | Обязательность |
|---|---|---|
| `file` | string | Да |
| `role` | string | Нет |
| `caption` | string | Нет |
| `alt` | string | Нет |

`role` описывает назначение материала, например:

- `reference`;
- `symptom`;
- `diagnostic`;
- `operation`;
- `tool`;
- `component`.

Каждый файл должен быть зарегистрирован в `assets`. Один файл может использоваться в нескольких блоках и технических сущностях. Повторное включение файла в `assets` не допускается.

## 18.12. Идентификаторы и связи

Идентификаторы сущностей должны быть уникальны в пределах соответствующих массивов.

Все ссылки между сущностями должны проверяться:

- объект, на который ссылается `parent_object_id`, должен существовать в `objects`;
- симптомы должны ссылаться на существующие объекты;
- причины должны ссылаться на существующие симптомы;
- диагностические процедуры должны ссылаться на существующие инструменты;
- переходы должны ссылаться на существующие шаги той же диагностической процедуры;
- шаги диагностики должны ссылаться на существующие записи `safety`, если указаны `safety_refs`;
- операции должны ссылаться на существующие диагностические процедуры, инструменты, материалы и предупреждения;
- `applies_to` должен ссылаться на существующие диагностические процедуры и/или операции;
- мультимедиа должны ссылаться на существующие файлы `assets`.

Ссылки на отсутствующие сущности являются ошибкой импорта.

## 18.13. Общие ограничения технических данных

Структурированные данные являются описанием знаний и процедур. Они не являются исполняемой программой.

Наличие диагностических переходов не означает автоматического выполнения измерений, управления оборудованием или постановки окончательного диагноза.

Внешний ИИ должен формировать технические данные с учётом фактической применимости к описанному объекту. Если информация носит общий характер и не подтверждена для конкретной модели, это должно быть явно обозначено в описании соответствующей сущности.
