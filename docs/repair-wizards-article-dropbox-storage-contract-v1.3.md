# Контракт хранения медиа статей в Dropbox

**Статус:** проектное решение для реализации  
**Формат статьи:** 1.3  
**Целевой контур проверки:** `script/template/repair_api_test_page`

## 1. Цель и границы

Все бинарные файлы статей (обложки, изображения блоков, галерей, шагов и 3D-модели с зависимостями) должны храниться в существующем Dropbox-хранилище проекта.

Не создаём отдельное файловое хранилище `/uploads/blog/{article_id}/` и не используем URL вида `/media/...` для новых импортированных файлов.

Импорт и операции со статьями выполняются через `repair_api_test_page`. Получение бинарного содержимого по идентификатору использует уже существующий файловый механизм проекта: `dropbox/file/{dl_id}` (клиентский модуль `src/app/state/api/dropbox.ts`). Это не новый внешний сервис и не другой API base URL.

## 2. Каноническая идентификация файла

Путь внутри ZIP остаётся логическим ключом статьи. Сервер не заменяет его числом и не удаляет:

```json
{
  "file": "media/cover.jpg",
  "type": "image",
  "format": "jpg",
  "size_bytes": 245000,
  "dl_id": 12345
}
```

Правила:

1. `assets[].file` — исходный относительный путь из ZIP; он сохраняется для аудита, диагностики и сопоставления ссылок.
2. `assets[].dl_id` — серверный числовой ID записи в `dropbox_link`; его назначает только сервер при импорте.
3. `file` во всех ссылках статьи (`cover`, `blocks`, `technical_knowledge`) остаётся относительным путём, как в формате 1.3.
4. Каждый путь из `assets` загружается в Dropbox ровно один раз на статью.
5. Все повторные ссылки на один путь используют тот же `dl_id` через сопоставление `assets[].file → assets[].dl_id`.
6. Клиент не должен угадывать ID, строить URL из пути или обращаться к `/media/`.

Таким образом, исходная структура контента формата 1.3 остаётся читаемой, а Dropbox ID является серверной метаинформацией реестра файлов.

## 3. Регистрация и загрузка

Сервер использует существующий шаблон регистрации файлов:

1. Проверяет файл из ZIP: нормализованный путь, размер, MIME/формат и соответствие записи `assets`.
2. Создаёт запись в `dropbox_link` с метаданными файла: исходное имя, имя загрузки, MIME-тип, размер и время создания.
3. Получает ID созданной записи — `dl_id`.
4. Передаёт байты в существующую функцию `upload_to_dropbox()`.
5. Проверяет ответ Dropbox на ошибку.
6. Сохраняет ответ Dropbox в JSON записи и устанавливает режим публичного чтения, соответствующий существующему контракту `private=0`.
7. Добавляет `dl_id` в соответствующий элемент `assets`.
8. Сохраняет статью только после успешной загрузки всех её файлов.

Не следует создавать собственную реализацию Dropbox-клиента или дублировать механизм загрузки из клиентского модуля.

### Доступ

Медиа опубликованной статьи должно читаться публично через существующий `dropbox/file/{dl_id}` endpoint. При создании записей необходимо использовать тот же набор связей владельца/пользователя, который принят существующими загрузками, если он требуется серверной проверкой доступа. Нельзя считать доступ публичным только на основании наличия строки в `dropbox_link`: это подтверждается интеграционным тестом чтения без авторизации.

## 3.1. Использование существующего файлового API для ручного переноса

Для переноса уже существующих медиафайлов (в том числе старых статей) используется **не прямое обращение к Dropbox SDK**, а файловый endpoint нашего API:

```
POST {API_BASE_URL}/dropbox/file/
```

Базовый URL берётся из текущего окружения приложения (в Preview — URL тестового backend). Нельзя подставлять production-домен или собирать адрес из старых абсолютных ссылок статьи.

Клиентская реализация и подтверждённый контракт в репозитории:
- `src/app/state/api/dropbox.ts` — `uploadFile(name, base64, privacy, userId?)`;
- `src/app/state/api/dropbox.ts` — `updateFile(dl_id, base64?, privacy?, userId?)`;
- `src/app/state/api/request.ts` — POST сериализует объектные поля как form-urlencoded значения, вложенные объекты сериализуются в JSON; авторизационные `token` и `u_hash` добавляются из текущей сессии.

Для новой загрузки клиент вызывает:

```ts
uploadFile(originalFileName, base64FileContents, 0)
```

Фактическое тело API содержит поле `file` — JSON-строку с полями:
- `name` — исходное имя файла;
- `base64` — содержимое файла в Base64;
- `private` — уровень доступа (тип клиента: `-1 | 0 | 1`).

При необходимости также передаётся `u_id`. Endpoint возвращает `dl_id`; клиентская функция принимает только положительный числовой ID. Полученный ID записывается в `assets[].dl_id`, а ссылки статьи сопоставляются с ним через исходный путь `assets[].file`.

Чтение уже загруженного файла выполняется через:

```
POST {API_BASE_URL}/dropbox/file/{dl_id}
```

Проверка результата обязательна: ответ должен быть бинарным, с ожидаемым MIME-типом и фактическим содержимым файла (не JSON-ошибкой). Проверять на том же API base URL, который использовался для загрузки.

**Проверенный backend-контракт (исходники найдены):**

Реализация находится в приватном репозитории `BuevichRoman/universal-backend`, ветка `audit/backend-pilot`, проверенный HEAD `3934234d1f30b70abb3213217e539de5acb76899`:
- `public_html/taxi/controllers/c_api.php` — диспетчер маршрута `/dropbox/file/`;
- `public_html/taxi/models/api.php` — методы `createDropboxFile()` (строка 13972), `selectDropboxFile()` (строка 14251), `deleteDropboxFile()` и `getDropboxFileData()`;
- `public_html/taxi/models/m_functions.php` — `upload_to_dropbox()` (строка 4753), `download_from_dropbox()` (строка 4812), `update_dropbox_access_token()` и `set_header_content_disposition()`.

Диспетчер маршрутизирует:
- `POST /dropbox/file/` при наличии `$_POST['file']` → `createDropboxFile($_POST['file'])`;
- `POST /dropbox/file/{dl_id}` → `selectDropboxFile($dl_id)`;
- `POST /dropbox/file/{dl_id}/del` → удаление;
- `POST /dropbox/file/{dl_ids}/select` → метаданные файлов.

Для записи требуется авторизованная сессия (`$_SESSION[UID]`). Поле `file` должно содержать JSON-строку. При новой загрузке обязательны:
- `base64` — Data URL вида `data:<mime>;base64,<payload>`;
- `name` — исходное имя (необязательно для кода, тогда сервер использует имя `file`);
- `private` — необязательное числовое значение доступа;
- `u_id` — необязательное, только для назначения файла другому пользователю; обычному пользователю чужой `u_id` запрещён, роль 4 может назначать.

Сервер декодирует Data URL и Base64, извлекает MIME и байты; создаёт `dropbox_link` с JSON-полями `name`, `name_upload`, `type`, `size` (`name_upload` обрезается до 115 символов); вставляет связь в `users_dropbox_link` для текущего пользователя; вызывает `upload_to_dropbox($content, $filename_upload, $id_dropbox_link)`; сохраняет `response.data` в JSON и возвращает `{code:'200', status:'success', data:{dl_id:<id>}}`. При ошибке загрузки возвращается ошибка API. Связь `users_dropbox_link` создаётся автоматически при обычной новой загрузке.

**Правила `private`, подтверждённые `selectDropboxFile()`:**
- `-1` — чтение разрешено без авторизованного пользователя;
- `0` — чтение разрешено авторизованному пользователю; анонимный запрос отклоняется;
- `1` — авторизованному пользователю разрешено только при наличии связи с ним в `users_dropbox_link`;
- удалённая запись (`deleted != 0`) не выдаётся.

Следовательно, значение `0` из клиентского примера нельзя считать публичным для посетителей без входа: анонимный запрос с `private=0` отклоняется. Для действительно анонимно доступного медиа backend требует `private=-1`. Для авторизованного пользователя `private=0` не требует связи с владельцем; `private=1` требует запись в `users_dropbox_link`. Отдельное исключение — роль 4: в `selectDropboxFile()` для неё проверка `private` пропускается. Для статьи №7, доступной читателям без входа, при загрузке необходимо явно передавать `private=-1` и проверять чтение без авторизации.

`selectDropboxFile()` получает `name_upload` и `type` из JSON и вызывает `download_from_dropbox(name_upload, dl_id, type)`. Метод сам не формирует JSON-ответ с файлом: `download_from_dropbox()` напрямую отправляет бинарное тело и завершает выполнение через `exit`, когда cURL возвращает `true`. Функция выставляет `Content-Type` из сохранённого MIME, `Content-Length` из ответа Dropbox, `Content-Disposition: inline` (с UTF-8 filename) и `Access-Control-Expose-Headers: Content-disposition`. При ошибке Dropbox возвращается API-ошибка. На тестовом Preview ранее уже подтверждён фактический ответ для `dl_id=213`: HTTP 200, `Content-Type: image/svg+xml`, `Content-Disposition: inline` и тело SVG.

Удаление не является физическим удалением строки: `deleteDropboxFile()` удаляет объект через `delete_from_dropbox()`, удаляет связи пользователя, затем выставляет `deleted=1` и сохраняет данные удаления в JSON. Для миграции это действие не требуется.

### Чек-лист переноса существующей статьи

1. Прочитать полную запись статьи и сохранить исходный JSON как резервную копию.
2. Составить инвентаризацию всех медиа-ссылок: обложка, блоки, галереи, шаги, 3D-модели и зависимости.
3. Для каждого уникального файла получить исходные байты, исходное имя и MIME-тип. Не загружать повторно один и тот же файл, используемый в нескольких местах.
4. Загрузить каждый файл через `uploadFile()` / `POST dropbox/file/` с корректным уровнем доступа.
5. Проверить каждый возвращённый `dl_id` чтением `dropbox/file/{dl_id}`: HTTP 200, корректный Content-Type и содержимое.
6. Обновить JSON статьи: сохранить текст, порядок и структуру блоков; добавить/обновить `assets[].dl_id`; заменить только ссылки на медиа в соответствии с согласованной схемой формата 1.3.
7. Обновлять запись статьи только после успешной проверки всех файлов. Не удалять исходные файлы и не трогать другие статьи.
8. Повторно запросить статью через `getBlogTopicById` и проверить её отображение в Preview и Network.
9. Зафиксировать в журнале ID статьи, старые пути, новые `dl_id`, MIME-типы, размеры и результаты проверок.

Для статьи с ID 7 этот чек-лист применяется адресно; массовый перенос остальных статей не входит в эту операцию.

## 4. Транспорт импорта

Все действия управления статьёй выполняются через:

```
POST /script/template/repair_api_test_page/
```

Операции:

- `validateBlogImport` — принимает ZIP через multipart-поле `archive`, проверяет структуру и содержимое; не создаёт постоянные Dropbox-файлы.
- `previewBlogImport` — использует временный токен проверки и показывает статью до сохранения. Временные файлы обслуживаются из временной области импорта, а не из постоянного Dropbox-хранилища.
- `importBlogPost` — после подтверждения загружает файлы в Dropbox, добавляет ID в `assets`, сохраняет JSON статьи и запись статьи.

Файловое чтение после импорта выполняется существующим endpoint `dropbox/file/{dl_id}` на том же настроенном API base URL.

## 5. Контракт выдачи статьи клиенту

Детальный ответ должен содержать:

- исходные `blocks` и ссылки в них;
- `assets` с исходными `file` и серверными `dl_id`;
- `cover_file_id` — ID файла обложки, найденный по `cover.file` в реестре assets;
- прежние поля статьи, не связанные с медиа.

Список статей должен возвращать `cover_file_id` для карточек. Не следует передавать числовой Dropbox ID в поле с названием `cover_url`.

На клиенте строится карта `file → dl_id`. Рендерер получает эту карту/реестр assets и для медиа использует числовой ID. Числовые источники загружаются через существующий `useFileById()` / `fetchFile()`; URL-строки остаются поддерживаемыми только для обратной совместимости со старыми статьями.

Для 3D-модели байты Dropbox-файла преобразуются в object URL, который передаётся в `model-viewer`. Object URL отзывается при размонтировании/смене файла.

## 6. Ошибки и согласованность

- Ошибка загрузки любого файла запрещает сохранение статьи.
- При ошибке после частичной загрузки выполняется компенсирующая очистка уже созданных Dropbox-записей/объектов либо они помечаются так, чтобы существующий сборщик мусора гарантированно удалил их.
- Нельзя оставлять опубликованную/сохранённую статью со ссылкой на отсутствующий `dl_id`.
- Нельзя удалять Dropbox-файл только потому, что удалена одна ссылка на него: перед удалением проверяется отсутствие ссылок из других статей и блоков.
- Повторный импорт не должен загружать файлы повторно, если операция распознана как повтор той же подтверждённой операции. Правило идемпотентности привязывается к токену импорта/идентификатору операции, а не к имени файла.

## 7. Совместимость

- Существующие статьи с URL и относительными путями продолжают отображаться по старому механизму.
- Новые импорты используют `assets[].dl_id`.
- Неизвестные клиенту дополнительные поля в JSON сохраняются.
- Внешний формат ZIP не требует знания Dropbox ID: `dl_id` генерируется только сервером и не включается автором в исходный ZIP.

## 8. Обязательные интеграционные проверки

1. Импорт статьи с обложкой, одиночным изображением, галереей, изображением шага и 3D-моделью.
2. Проверка: один уникальный `assets[].file` создаёт ровно один `dl_id`, даже если используется в нескольких блоках.
3. Проверка ответа `getBlogTopicById`: все ID присутствуют, все ссылки разрешаются через assets.
4. Проверка карточки списка: `cover_file_id` возвращается и загружается.
5. Чтение каждого файла через `dropbox/file/{dl_id}` без авторизации после публикации; для этого требуется `private=-1`.
6. Проверка MIME-типа и фактического содержимого для изображения и GLB.
7. Ошибка Dropbox на N-м файле: статья не сохраняется, частично загруженные файлы очищаются или гарантированно попадают под GC.
8. Повтор подтверждения импорта не создаёт дубликаты файлов и статей.
9. Старые статьи с URL продолжают отображаться.
10. В Network нет запросов к `/media/...` для новых Dropbox-статей.

## 9. Что не считается подтверждённым до теста

Следующие детали должны быть установлены интеграционным тестом в тестовом контуре, а не предполагаться по названию полей:

- точный формат JSON-ответа `dropbox/file/{dl_id}` и MIME-заголовки;
- поведение удаления Dropbox-файла и сборщика мусора;
- возможность безопасной компенсации частичной загрузки.

До подтверждения этих пунктов нельзя включать массовый импорт или менять рабочий серверный шаблон.
