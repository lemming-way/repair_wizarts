# Предварительные технические решения

# Доработка статей и комментариев Repair Wizards

**Версия документа:** 1.1  
**Статус:** техническое дополнение к согласованию и реализации

## 1. Назначение и связь с основным ТЗ

Документ фиксирует предварительные технические решения по реализации раздела статей и комментариев Repair Wizards в существующей архитектуре Universal Backend.

Документ применяется совместно с:

1. Основным ТЗ «Доработка раздела статей и комментариев Repair Wizards», версия 1.1.
2. Приложением № 1 «Спецификация формата статей Repair Wizards для внешних ИИ», версия 1.3.
3. Приложением № 2 «Техническая реализация хранения, импорта и мультимедийного отображения статей Repair Wizards», версия 1.3.

Основное ТЗ определяет функциональность и бизнес-правила. Приложения № 1 и № 2 определяют формат содержимого, импорт, хранение и отображение статей. Настоящий документ определяет рекомендуемый способ реализации в существующем проекте.

В части формата статьи, импорта, хранения редакций и отображения приоритет имеют Приложения № 1 и № 2. В части пользовательских сценариев, прав и бизнес-правил приоритет имеет основное ТЗ. Настоящий документ не может ослаблять или изменять эти требования.

Если фактическая структура БД или существующий API не позволяют реализовать решение буквально, разработчик должен описать расхождение и предложить минимальное изменение до начала соответствующей реализации.

## 2. Общие архитектурные решения

### 2.1. Backend

Использовать существующий механизм:

`script/template/repair_api`

Новые операции реализовать как actions внутри:

`script_templates/repair_api.php`

Обоснование:

- Repair API уже использует этот механизм;
- он работает в контексте Universal Backend;
- использует общую авторизацию, подключение к БД и SQL helpers;
- не требуется создавать отдельный сервис или дублировать инфраструктуру.

Новые actions должны соблюдать существующие соглашения проекта по входным параметрам, формату ответов, обработке ошибок, авторизации и работе с БД. Перед реализацией необходимо изучить фактический код `repair_api.php` и соседние actions. Приведённые в документе названия методов являются предлагаемыми логическими именами; окончательные имена и формат вызова должны соответствовать действующим соглашениям API.

### 2.2. Frontend

Использовать существующую React + TypeScript архитектуру.

Вместо mock data и временных заглушек подключить реальные методы API. Не создавать параллельную архитектуру состояния или отдельный механизм авторизации для статей.

Для отображения содержимого статьи использовать единый `ArticleRenderer` в Preview и на публичной странице. Не создавать два независимых рендерера.

### 2.3. Область изменений

Изменения ограничить:

- классификатором статей;
- каталогом и страницами статей;
- импортом и хранением редакций;
- согласованием и публикациями;
- комментариями и вложенными ответами.

Не затрагивать заказы, чаты, таблицу `message` и остальные бизнес-процессы Universal Backend.

## 3. Предварительная техническая сверка

До изменения кода фрилансер должен провести короткую техническую сверку актуальной dev-среды и зафиксировать результат.

Проверить:

1. Реальные структуры таблиц `blog_topic` и `blog_post`.
2. Связи статей с пользователями и классификатором.
3. Наличие таблицы комментариев или функционально аналогичной структуры.
4. Реальные поля статусов, публикации, даты изменения и архивирования.
5. Существующие механизмы хранения JSON и файлов статей.
6. Существующие методы и заглушки во frontend.
7. Текущие actions и соглашения по формату ответов `repair_api.php`.
8. Соглашения по SQL helpers, транзакциям, блокировкам и обработке ошибок.
9. Используемые типы идентификаторов, движок таблиц и наличие внешних ключей.

По итогам сверки подготовить краткую таблицу: «существующий механизм / требуемая функциональность / предлагаемое изменение».

Не создавать новые поля, таблицы или методы, если аналогичная функциональность уже существует и может быть безопасно использована. Не проводить миграции и очистку тестовых данных без отдельного согласования.

## 4. Классификатор статей

Использовать существующую таблицу `blog_topic`.

Не использовать `sprset`: она не является источником классификатора статей в рамках этой доработки.

### 4.1. Метод `getBlogTopics`

Назначение: получить дерево классификатора.

Предлагаемый результат для каждого раздела:

- идентификатор;
- название;
- идентификатор родительского раздела;
- уровень вложенности;
- порядок отображения.

Предпочтительно возвращать полный доступный классификатор одним запросом, чтобы клиент мог построить дерево без отдельных запросов для каждого уровня.

### 4.2. Метод `getBlogTopicById`

Предварительно не считать обязательным. Добавлять только при наличии конкретного сценария, который не покрывается `getBlogTopics`.

### 4.3. Область управления классификатором

В рамках данной доработки предусматриваются получение дерева, выбор темы при создании/импорте и фильтрация каталога. Создание, переименование, перемещение и удаление разделов классификатора не входят в объём работ, если это отдельно не подтверждено основным ТЗ.

При импорте предложенная внешним инструментом тема из `article.json` должна сопоставляться с существующим `blog_topic`. Внешний пакет не назначает идентификаторы разделов самостоятельно.

## 5. Получение списка статей

### 5.1. Метод `getBlogPosts`

Основной метод каталога статей.

Предлагаемые параметры:

| Параметр | Назначение |
|---|---|
| `topic_id` | Выбранный раздел классификатора |
| `author_id` | Идентификатор автора |
| `page` | Номер страницы |
| `limit` | Количество статей на странице |
| `status` | Запрашиваемый статус в пределах прав текущего пользователя |

Фильтрация:

1. По классификатору — с включением дочерних разделов выбранного раздела.
2. По автору — по идентификатору автора.
3. При одновременном использовании фильтров применяется логическое AND.
4. Пустой параметр фильтра не ограничивает выборку.
5. Параметры пагинации должны проверяться и ограничиваться сервером.

Права доступа определяются сервером, а не значением параметра `status`:

- публичный каталог возвращает только опубликованные статьи;
- автор получает собственные статьи и редакции в пределах разрешённых ему статусов;
- модератор/администратор получает статьи, доступные его роли;
- передача клиентом статуса не может расширить доступ.

### 5.2. Результат

Для каждой статьи возвращать необходимые каталогу данные:

- идентификатор статьи;
- название;
- краткое описание;
- автора и его идентификатор;
- классификатор;
- дату публикации;
- дату последнего изменения;
- публичный статус либо статус, доступный текущей роли.

Не передавать полный JSON и технические данные статьи в списке каталога без отдельной необходимости.

## 6. Создание, импорт и редактирование статей

### 6.1. Принцип хранения содержимого

Содержимое статьи готовится вне Repair Wizards и передаётся ZIP-архивом по спецификации формата 1.3. Архив содержит `article.json` и каталог `media/`.

Не реализовывать передачу полного содержимого статьи как обычного набора полей `addBlogPost` и не создавать встроенный редактор блоков.

Обязательные требования к импорту, проверке ZIP, JSON, файлов, временным ресурсам, хранению и Preview определены Приложениями № 1 и № 2.

### 6.2. Создание новой статьи

Логическая операция создания статьи должна выполняться после:

1. серверной проверки ZIP-пакета;
2. успешной проверки структуры и содержимого;
3. формирования Preview;
4. подтверждения импорта пользователем.

После подтверждения создаётся новая статья со статусом `draft`.

Автор и начальный статус определяются сервером. Клиент не может назначить автора или произвольный статус.

Если существующий API использует action `addBlogPost`, его назначение необходимо адаптировать к этой модели: создание записи на основании подтверждённого импорта, а не приём произвольного текста/JSON от клиента.

До подтверждения не должно происходить частичного создания постоянной статьи. Временные файлы и результаты проверки должны очищаться при отмене, ошибке или истечении срока хранения временного импорта.

### 6.3. Редактирование метаданных

Логическая операция `editBlogPost` должна изменять только разрешённые метаданные, например:

- название;
- краткое описание;
- классификатор;
- другие существующие поля метаданных, предусмотренные моделью.

Операция не должна перезаписывать содержимое опубликованной или ожидающей согласования редакции произвольным JSON, полученным от клиента.

Сервер проверяет существование статьи, авторство или административные права и допустимость редактирования при текущем статусе. Дата изменения обновляется сервером.

### 6.4. Импорт новой редакции существующей статьи

Изменение содержимого существующей статьи выполняется импортом нового ZIP в явно выбранную статью.

До начала реализации необходимо проверить, позволяет ли существующая модель хранить одновременно:

- текущую опубликованную редакцию;
- новую редакцию, проходящую проверку и согласование.

Если не позволяет, разработчик должен предложить минимальное изменение хранения и согласовать его до реализации. Нельзя перезаписывать публичный JSON при загрузке или отправке новой редакции на согласование.

Пока новая редакция не одобрена, публичная страница продолжает показывать последнюю опубликованную редакцию. После одобрения выполняется атомарное переключение публичной версии. Предыдущая версия не должна теряться до успешного завершения переключения.

Для ещё не опубликованного черновика допускается замена его содержимого после успешной проверки и подтверждения автором.

Повторный импорт должен быть явно привязан к целевой статье. Он не должен случайно создавать дубликат или изменять другую статью.

### 6.5. Предварительный просмотр

Preview должен использовать тот же `ArticleRenderer`, что и опубликованная статья, и показывать фактический результат отображения импортируемой редакции.

Preview не публикует материал, не изменяет текущую публичную редакцию и использует контролируемые временные ссылки на медиафайлы.

## 7. Согласование и публикация

Изменение статуса должно выполняться отдельными серверными бизнес-операциями, а не произвольным изменением поля `status` через `editBlogPost`.

Предлагаемые логические операции:

| Метод | Назначение |
|---|---|
| `submitBlogPost` | Отправить черновик/редакцию на согласование |
| `approveBlogPost` | Одобрить и опубликовать статью или новую редакцию |
| `returnBlogPost` | Вернуть автору на доработку |
| `rejectBlogPost` | Отклонить публикацию |
| `archiveBlogPost` | Перевести статью в архив |

Статусы основного жизненного цикла:

- `draft`;
- `pending`;
- `published`;
- `revision`;
- `rejected`;
- `archived`.

Перед реализацией сопоставить их с фактическими полями и статусами `blog_post`. Не создавать дублирующие поля и не менять существующую модель без необходимости.

Каждая операция проверяет роль, право на действие, текущий статус и допустимость перехода. Повторный запрос не должен приводить к повторной публикации или повреждению данных.

При одобрении новой редакции опубликованной статьи обновление указателя/связи с публичной версией и необходимые изменения статуса должны выполняться атомарно. Если операция завершается ошибкой, старая публичная версия остаётся доступной.

## 8. Комментарии: структура хранения

Использовать существующую таблицу комментариев, если она уже реализует необходимые требования. Если её нет или её модель не поддерживает произвольную вложенность, предусмотреть отдельную таблицу `blog_comment`.

Предварительная логическая структура:

| Поле | Назначение |
|---|---|
| `id` | Первичный ключ |
| `blog_post_id` | Идентификатор статьи |
| `parent_comment_id` | Идентификатор родительского комментария, NULL для корневого |
| `user_id` | Автор |
| `text` | Текст комментария |
| `created_at` | Дата и время создания |
| `updated_at` | Дата и время последнего редактирования |
| `deleted_at` | Дата мягкого удаления, если применяется |

Реальные имена полей и типы должны соответствовать существующим соглашениям БД. В основном ТЗ логический идентификатор статьи может называться `article_id`; при реализации используется фактическое поле связи с `blog_post`, без изменения смысла.

Основное решение — самоссылочная связь `parent_comment_id`, а не фиксированные поля для первого и второго уровней.

Предлагаемые индексы после сверки схемы:

- `(blog_post_id, parent_comment_id, id)`;
- `(parent_comment_id, id)`;
- `(user_id)`.

Проверить возможность и целесообразность внешних ключей на статью, родительский комментарий и пользователя. Не вводить каскадное физическое удаление комментариев и ответов.

## 9. Получение дерева комментариев

### 9.1. Метод `getBlogComments`

Параметр:

- `blog_post_id`.

Метод возвращает комментарии статьи с ответами произвольной глубины.

Каждый объект содержит:

- идентификатор;
- идентификатор статьи;
- идентификатор родителя;
- автора и его идентификатор;
- текст;
- дату создания;
- дату редактирования;
- признак удаления;
- признаки `can_edit` и `can_delete`.

Предпочтительно получать все комментарии статьи одним запросом и строить дерево на сервере или клиенте. Не выполнять отдельный SQL-запрос для каждого родителя (N+1).

### 9.2. Порядок

Порядок создания внутри каждой группы определяется по возрастанию `id`, если фактический механизм генерации ID обеспечивает монотонность в рамках таблицы. `created_at` используется для отображения времени, но не является критерием определения последнего комментария.

Если существующая схема не обеспечивает пригодный монотонный ID, до реализации согласовать единый надёжный ключ последовательности. Нельзя использовать неоднозначное сравнение временных меток с недостаточной точностью.

## 10. Добавление комментариев и ответов

### 10.1. Метод `addBlogComment`

Предлагаемые параметры:

- `blog_post_id`;
- `parent_comment_id` (NULL для комментария непосредственно к статье);
- `text`.

Сервер:

1. Проверяет авторизацию.
2. Проверяет существование статьи и право комментировать её.
3. Проверяет, что статья допускает комментирование.
4. Если указан родитель, проверяет его существование и принадлежность той же статье.
5. Проверяет допустимость ответа на удалённый комментарий согласно правилу ниже.
6. Проверяет длину текста — не более 1000 символов Unicode, а не байтов UTF-8.
7. Определяет автора из текущего контекста авторизации.
8. Сохраняет комментарий в транзакции с общей блокировкой соответствующей группы.

Один метод обслуживает корневые комментарии и ответы любого уровня.

### 10.2. Ответы на удалённые комментарии

Рекомендуемое правило: разрешить добавлять ответы к удалённому комментарию, если статья и обсуждение остаются открытыми для комментирования.

Удалённая запись сохраняет место в дереве и выступает родительским узлом; её текст заменяется нейтральной отметкой «Комментарий удалён». Это позволяет продолжать обсуждение, не восстанавливая удалённый текст.

## 11. Редактирование и удаление комментариев

Методы:

- `editBlogComment`;
- `deleteBlogComment`.

### 11.1. Правило авторства и последнего комментария

Редактировать или удалять комментарий может только его автор.

Дополнительно комментарий должен быть последним в своей группе вложенности.

Группа определяется сочетанием:

`blog_post_id + parent_comment_id`

Следовательно:

- все корневые комментарии одной статьи образуют одну группу (`parent_comment_id = NULL`);
- все ответы на комментарий №10 образуют другую группу (`parent_comment_id = 10`);
- ответы на каждый отдельный комментарий образуют самостоятельные группы;
- добавление ответа в дочернюю группу не меняет права в родительской группе.

### 11.2. Определение последнего комментария

Последним считается комментарий с максимальным `id` в соответствующей группе, включая комментарии, которые впоследствии были мягко удалены.

Удаление более позднего комментария не возвращает право редактирования или удаления предыдущего комментария.

Удалённый комментарий нельзя редактировать или удалять повторно. Для проверки последнего комментария учитываются все созданные записи группы независимо от `deleted_at).

Это правило не позволяет обходить ограничение «только последний комментарий» удалением более позднего сообщения.

### 11.3. Серверная проверка

Для каждой операции сервер проверяет:

1. Пользователь авторизован.
2. Комментарий существует.
3. Комментарий не удалён.
4. Текущий пользователь является автором комментария.
5. Комментарий является последним по `id` в своей группе.
6. Статья и обсуждение находятся в состоянии, допускающем операцию.

Значения `can_edit` и `can_delete` из клиентского запроса не являются основанием для предоставления права.

### 11.4. Атомарность и единый протокол блокировок

Проверка последнего комментария и изменение записи должны быть защищены от гонки с параллельным добавлением комментария в ту же группу.

Все операции добавления, редактирования и удаления обязаны использовать один и тот же протокол блокировки.

Логический порядок:

1. Начать транзакцию InnoDB.
2. Заблокировать запись, представляющую группу:
   - для корневой группы — запись статьи;
   - для группы ответов — запись непосредственного родительского комментария.
3. Для операций с ответами дополнительно убедиться, что родитель существует и принадлежит той же статье.
4. После получения блокировки определить максимальный `id` в группе, включая мягко удалённые записи.
5. Для редактирования/удаления проверить, что изменяемый комментарий имеет этот максимальный ID и принадлежит текущему пользователю.
6. Выполнить добавление, изменение или мягкое удаление.
7. Зафиксировать транзакцию.

Добавление комментария в группу должно блокировать ту же запись группы до вставки. Нельзя реализовать блокировку только в `editBlogComment` или только в `deleteBlogComment`, оставив `addBlogComment` без неё.

Для ответа на комментарий блокируется непосредственная запись родителя, а не вся цепочка предков. Таким образом, добавление ответа в дочернюю группу не блокирует и не меняет права в группе родительского комментария.

Если конкретная схема не позволяет надёжно блокировать запись группы (например, из-за отсутствия стабильной записи-родителя), разработчик должен предложить согласованный механизм сериализации операций до реализации. Одна проверка `MAX(id)` без общей блокировки не считается достаточной.

### 11.5. Мягкое удаление и сохранение дерева

Рекомендуется мягкое удаление через `deleted_at` либо эквивалентный существующий механизм.

При удалении комментария:

- запись не удаляется физически;
- дочерние ответы не удаляются;
- структура дерева сохраняется;
- вместо текста показывается нейтральная отметка «Комментарий удалён»;
- авторство и технические данные сохраняются в объёме, необходимом для целостности и аудита;
- удалённый комментарий исключается из редактирования и повторного удаления;
- его ID продолжает участвовать в определении последнего комментария группы.

Физическое удаление комментария с ответами и каскадное удаление дочерних записей не допускаются в рамках этой доработки.

## 12. Права доступа и признаки действий

Все права определяются на сервере.

Клиент может получать признаки:

- `can_edit`;
- `can_delete`.

Они рассчитываются для каждого комментария с учётом:

- текущего пользователя;
- авторства;
- статуса удаления;
- положения комментария в его группе;
- текущего состояния статьи и обсуждения.

Эти признаки нужны для управления интерфейсом, но не заменяют повторную проверку прав в момент выполнения операции.

Публичный просмотр статьи, доступ к черновикам, Preview, административные операции и доступ к `technical_knowledge` должны соответствовать правилам основного ТЗ и приложений.

## 13. Обработка ошибок

API должен различать бизнес-ошибки и технические ошибки.

Бизнес-ошибки:

- пользователь не авторизован;
- недостаточно прав;
- статья не найдена;
- комментарий не найден;
- родительский комментарий относится к другой статье;
- статья или обсуждение не допускают комментирование;
- превышена длина текста;
- комментарий уже удалён;
- комментарий больше не является последним в группе;
- недопустимый переход статуса;
- новая редакция не может быть опубликована в текущем состоянии.

Технические ошибки:

- ошибка базы данных;
- ошибка транзакции;
- конфликт блокировки или deadlock;
- ошибка сохранения файла;
- ошибка проверки/распаковки ZIP;
- ошибка атомарного переключения опубликованной редакции.

Ответы должны соответствовать существующему формату Repair API и содержать стабильный код ошибки, пригодный для обработки frontend. Не возвращать клиенту внутренние SQL-тексты, трассировки и секретные сведения.

Конфликт «комментарий больше не последний» должен быть отдельным понятным результатом, а не общей ошибкой сервера.

## 14. Безопасность

Обязательные требования:

- параметризованные SQL-запросы;
- проверка и нормализация входных идентификаторов;
- серверное определение автора;
- серверная проверка ролей и прав на каждую операцию;
- защита от SQL-инъекций;
- безопасный вывод текстов комментариев и содержимого статей;
- защита от XSS;
- проверка принадлежности родительского комментария той же статье;
- транзакции и общий протокол блокировок для критичных операций;
- отсутствие доверия к `can_edit`, `can_delete` и другим клиентским признакам;
- безопасная обработка ZIP и медиафайлов по Приложению № 2;
- запрет исполнения кода из блоков статей и содержимого `technical_knowledge`.

Для проверки длины комментария использовать подсчёт Unicode-символов, а не длины строки в байтах.

## 15. Тестирование

### 15.1. Классификатор и каталог

Проверить:

- получение полного дерева `blog_topic`;
- корректное отображение уровней и порядка;
- фильтрацию по каждому уровню классификатора;
- включение дочерних разделов при выборе родительского;
- фильтр по автору;
- совместную работу фильтров;
- сброс одного фильтра без сброса другого;
- пагинацию и ограничение `limit`;
- пустые результаты;
- невозможность получить закрытые статусы через публичный запрос.

### 15.2. Статьи и публикации

Проверить:

- создание новой статьи через подтверждённый импорт;
- определение автора и начального статуса сервером;
- проверку прав;
- Preview до подтверждения импорта;
- отсутствие постоянной записи при отмене импорта;
- редактирование только разрешённых метаданных;
- запрет изменения содержимого через `editBlogPost`;
- отправку на согласование;
- одобрение, возврат на доработку, отклонение и архивирование;
- сохранение опубликованной редакции при импорте новой;
- публикацию новой редакции только после одобрения;
- атомарность переключения публичной версии;
- сохранность старой версии при ошибке;
- корректное отображение старых статей и форматов 1.2/1.3.

### 15.3. Комментарии и вложенность

Проверить:

- корневые комментарии;
- ответы;
- ответы на ответы;
- несколько уровней вложенности;
- корректное построение дерева одним запросом;
- принадлежность родителя той же статье;
- добавление ответа в старую ветку;
- разрешённое добавление ответа к мягко удалённому родителю;
- ограничение 1000 Unicode-символов;
- корректный порядок внутри каждой группы.

### 15.4. Редактирование и удаление

Проверить:

- редактирование последнего собственного комментария в корневой группе;
- запрет редактирования предыдущего комментария после добавления следующего;
- независимость прав в разных группах ответов;
- независимость родительской и дочерней групп;
- запрет изменения чужого комментария;
- запрет изменения удалённого комментария;
- мягкое удаление комментария с сохранением ответов;
- отсутствие каскадного удаления;
- сохранение ID удалённого комментария в последовательности группы;
- удаление последнего комментария не возвращает право на предыдущий;
- конкурентное добавление и редактирование в одной группе;
- конкурентное добавление и удаление в одной группе;
- одновременные операции в разных группах;
- корректную обработку deadlock/конфликта транзакций.

### 15.5. Безопасность

Проверить:

- неавторизованный доступ;
- попытку административной операции обычным пользователем;
- SQL-инъекции;
- XSS в статье и комментариях;
- подмену автора и статуса со стороны клиента;
- некорректные идентификаторы;
- попытку ответить на комментарий другой статьи;
- попытку редактировать/удалить чужой или не последний комментарий;
- ZIP Slip, абсолютные пути, подмену MIME/расширения и превышение лимитов по Приложению № 2.

## 16. Критерии готовности

Техническая реализация соответствует настоящему документу, если:

1. Новые backend-операции встроены в существующий `repair_api.php` и используют общую инфраструктуру.
2. Frontend использует реальные API вместо mock data и заглушек.
3. Классификатор читается из `blog_topic`.
4. Каталог поддерживает совместные фильтры и серверную пагинацию.
5. Содержимое новых и обновляемых статей поступает через ZIP-импорт.
6. Preview и опубликованная статья используют единый `ArticleRenderer`.
7. Опубликованная версия не заменяется до одобрения новой редакции.
8. Публикация новой редакции выполняется атомарно.
9. Комментарии поддерживают произвольную глубину вложенности.
10. Добавление, редактирование и удаление комментариев используют единый протокол блокировок по группе.
11. Редактирование и удаление доступны только автору последнего по ID комментария соответствующей группы.
12. Мягкое удаление не разрушает дерево и не возвращает право редактирования предыдущего комментария.
13. Все права проверяются на сервере.
14. Проверки из раздела 15 выполнены, критические сценарии проходят.
15. Изменения не затрагивают заказы, чаты и другие бизнес-процессы вне согласованной области.

## 17. Принципиальные ограничения

- Не менять модель заказов.
- Не изменять таблицу `message` и чатовые методы.
- Не проводить миграции и очистку старых тестовых данных без отдельного согласования.
- Не вводить отдельный backend для статей.
- Не перестраивать Universal Backend.
- Не создавать встроенный редактор содержимого статей.
- Не создавать отдельный механизм авторизации.
- Не исполнять программный код из статей.
- Не реализовывать диагностические сценарии, автоматические брифы и создание заказов.
- Не реализовывать аренду или бронирование инструментов.
- Не выполнять физическое каскадное удаление комментариев и ответов.
- Не менять согласованные правила публикации и комментариев без отдельного согласования.
