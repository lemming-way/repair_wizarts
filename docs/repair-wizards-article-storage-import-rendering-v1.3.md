# Приложение № 2

# Техническая реализация хранения, импорта и мультимедийного отображения статей Repair Wizards

**Версия документа:** 1.3  
**Соответствующая версия формата статей:** 1.3

## 1. Назначение

Документ определяет техническую реализацию хранения, импорта, проверки и отображения статей Repair Wizards, подготовленных во внешних ИИ и инструментах создания контента.

Документ является техническим дополнением к Приложению № 1.

Единый контракт обмена:

- `format_version = "1.3"` для новой версии формата;
- поддержка ранее согласованной версии `format_version = "1.2"`;
- структура `article.json`;
- единый набор типов блоков;
- единая структура ZIP;
- единый реестр файлов `assets`;
- необязательный объект `technical_knowledge` в формате 1.3.

При расхождении технических деталей с форматом обмена приоритет имеет Приложение № 1.

## 2. Существующая архитектура

Используются существующие компоненты проекта:

- Backend: PHP REST API;
- база данных: MySQL;
- Frontend: React + TypeScript SPA;
- API: `script/template/repair_api`;
- таблица статей: `blog_post`;
- таблица тем: `blog_topic`.

Необходимо использовать существующие механизмы авторизации, маршрутизации, проверки прав и работы с файлами.

Создание отдельной CMS или самостоятельной подсистемы публикаций не предусматривается.

До изменения структуры БД разработчик должен проверить фактическую схему таблиц и используемые поля.

## 3. Хранение статьи

Статья хранится в существующей таблице `blog_post`.

Если соответствующие поля отсутствуют, рекомендуется предусмотреть:

| Поле | Назначение |
|---|---|
| `content_json` | JSON-содержимое статьи |
| `content_format` | Тип содержимого |
| `content_version` | Версия формата |

Названия и типы полей согласуются с фактической схемой БД.

Заголовок, описание, автор, тема и статус публикации должны использовать существующие поля, если они уже предусмотрены.

### 3.1. Хранение файлов

Единственное постоянное файловое хранилище медиа статей — существующий Dropbox backend.

Каждый файл из `media/` загружается через `POST /api/v1/dropbox/file/` методом `createDropboxFile()`. В запрос передаются имя, Base64-содержимое, владелец и `private: -1` для публичного чтения опубликованной статьи. Ответ содержит `dl_id`.

В JSON статьи ссылки на медиа хранятся как `dropbox:{dl_id}`:

- `assets[].file`;
- `cover.file`;
- ссылки `file` и `image` в блоках;
- ссылки на файлы внутри `technical_knowledge.media_refs`.

Исходное имя и путь архива сохраняются в `assets[].source_file`. MIME-тип передаётся при загрузке и хранится в метаданных Dropbox. Бинарное содержимое не перекодируется: GLB и остальные файлы передаются без изменения байтов.

Frontend преобразует `dropbox:{dl_id}` в адрес существующего метода чтения `/api/v1/dropbox/file/{dl_id}`. Локальные пути `/uploads/blog` и `public/articles` не используются для медиа статей, импортированных в БД.

### 3.2. Хранение technical_knowledge

Объект `technical_knowledge` хранится внутри общего JSON статьи в поле `content_json`.

Для его элементов не создаются отдельные таблицы БД в рамках версии 1.3.

Backend должен сохранять объект целиком, включая:

- все известные поля;
- вложенные структуры;
- идентификаторы;
- связи между сущностями;
- значения массивов и объектов;
- неизвестные дополнительные поля, не используемые текущей версией Backend.

Backend не должен удалять неизвестные дополнительные поля при разборе, проверке, сохранении или выдаче статьи.

Проверка известных полей не должна приводить к пересборке JSON только из распознанных полей с потерей остального содержимого.

## 4. Приём ZIP-архива

Система принимает архив:

```text
article.zip
├── article.json
└── media/
    ├── cover.jpg
    ├── image_001.webp
    ├── step_01.jpg
    ├── repair_model.glb
    └── model_texture.png
```

Backend принимает архив через существующий REST API.

До подтверждения импорта файлы размещаются во временной области.

## 5. Проверка архива

Backend выполняет безопасную распаковку и проверяет:

- наличие `article.json`;
- наличие `media/`;
- корректность структуры каталогов;
- отсутствие абсолютных путей;
- отсутствие ZIP Slip;
- количество файлов;
- размеры отдельных файлов;
- общий объём распакованных данных;
- отсутствие запрещённых файлов.

Имена и пути из ZIP нельзя использовать без проверки и нормализации.

## 6. Проверка JSON

Проверяется:

- корректность JSON;
- наличие обязательных корневых полей;
- `format_version`;
- поддерживаемая версия формата: 1.2 или 1.3;
- структура `topic`;
- структура `cover`;
- наличие `assets`;
- наличие `blocks`;
- корректность каждого типа блока;
- соответствие ссылок реестру `assets`;
- отсутствие произвольных HTML и JavaScript.

Неизвестный тип блока приводит к ошибке импорта.

Неизвестные дополнительные поля не должны приводить к ошибке только по причине того, что текущая версия Backend их не использует. Такие поля должны сохраняться в исходном JSON.

Для версии 1.2 объект `technical_knowledge` не требуется.

Для версии 1.3 объект `technical_knowledge` необязателен. Если он присутствует, выполняется дополнительная проверка по разделу 8.4.

## 7. Проверка реестра assets

Для каждого элемента `assets` Backend проверяет:

1. Наличие `file`.
2. Наличие `type`.
3. Наличие `format`.
4. Наличие `size_bytes`.
5. Уникальность пути.
6. Наличие файла в архиве.
7. Совпадение фактического размера.
8. Соответствие реального формата заявленному.
9. Допустимость типа ресурса.
10. Использование файла в статье.

Все ссылки из `cover`, `blocks` и `technical_knowledge` должны указывать на зарегистрированные файлы.

Один файл может использоваться в нескольких блоках и технических сущностях. Повторная регистрация одного пути в `assets` не допускается.

Неиспользуемые и незарегистрированные файлы не должны попадать в итоговое хранилище.

## 8. Проверка типов блоков

| Тип | Серверная проверка |
|---|---|
| `heading` | Уровень 2–4, наличие текста |
| `paragraph` | Наличие текста |
| `image` | Наличие файла, запись в `assets` |
| `gallery` | Не менее двух изображений, проверка каждого файла |
| `video` | Допустимый URL и поддерживаемая платформа |
| `list` | Допустимый стиль и наличие элементов |
| `quote` | Наличие текста |
| `callout` | Допустимый стиль и наличие текста |
| `steps` | Наличие массива шагов и обязательных полей каждого шага |
| `table` | Наличие заголовков, корректное количество ячеек в строках |
| `code` | Наличие текста и корректность поля языка |
| `model_3d` | Допустимый формат модели, наличие файла и зависимостей |

### 8.1. Проверка steps

Для каждого шага проверяются:

- `title`;
- `text`;
- наличие изображения, если оно указано;
- регистрация изображения в `assets`;
- наличие текста предупреждения, если оно указано.

Порядок шагов сохраняется.

### 8.2. Проверка table

Backend проверяет:

- наличие массива `headers`;
- наличие массива `rows`;
- непустой набор заголовков;
- соответствие количества ячеек количеству заголовков;
- допустимость типов значений.

Значения таблицы обрабатываются как текст. HTML не исполняется.

### 8.3. Проверка code

Backend проверяет:

- наличие `text`;
- наличие `language`;
- допустимость длины содержимого;
- отсутствие попыток использовать поле для выполнения кода.

Поле `language` используется для выбора подсветки синтаксиса на Frontend.

Само содержимое никогда не передаётся на выполнение.

### 8.4. Проверка technical_knowledge

Если в статье версии 1.3 присутствует `technical_knowledge`, Backend проверяет:

1. Корректность `schema_version`.
2. Типы и структуру присутствующих массивов.
3. Наличие обязательных полей сущностей.
4. Уникальность идентификаторов сущностей в пределах соответствующих массивов.
5. Корректность ссылок между техническими сущностями.
6. Корректность ссылок на диагностические шаги.
7. Корректность условий переходов.
8. Корректность ссылок на инструменты и материалы.
9. Корректность ссылок на `safety`.
10. Соответствие ссылок на изображения реестру `assets`.
11. Допустимость значений перечислений.
12. Отсутствие исполняемого кода и произвольных выражений в диагностических условиях.

Дополнительно проверяется:

- `objects.parent_object_id` ссылается на существующий объект;
- каждый `object_id` в симптоме существует;
- каждый `symptom_id` в причине существует;
- каждый `diagnostic_ref` в причине существует;
- каждый `required_tool_id` в диагностической процедуре существует;
- каждый `next_step_id` существует в пределах той же диагностической процедуры;
- каждый `safety_ref` диагностического шага существует;
- каждый `diagnostic_ref`, `tool_ref`, `material_ref` и `safety_ref` операции существует;
- ссылки в `safety.applies_to` указывают на существующие диагностические процедуры или ремонтные операции;
- все `media_refs.file` существуют в `assets`.

Для переходов проверяется допустимость оператора:

- `eq`;
- `ne`;
- `gt`;
- `gte`;
- `lt`;
- `lte`.

Для `response.type = "choice"` проверяется наличие массива `options` и полей `value`, `label` у каждого варианта.

Для `response.type = "number"` проверяются типы `min`, `max`, если они заданы, и условие `min <= max`.

Для завершающего шага `terminal = true` переходы не требуются.

Для незавершающего шага должно быть определено продолжение процедуры. Все переходы должны вести к существующим шагам той же процедуры.

Отсутствие необязательных массивов не является ошибкой.

Если `technical_knowledge` отсутствует, статья обрабатывается по обычным правилам своей версии.

Неизвестные дополнительные поля внутри `technical_knowledge` должны сохраняться без потери. Они не исполняются и не должны влиять на безопасность обработки известных полей.

В версии 1.3 Backend проверяет структуру и связи технических данных, но не оценивает фактическую правильность диагноза, измерений или ремонтных рекомендаций.

## 9. Проверка 3D-моделей

Для `model_3d` Backend проверяет:

- наличие файла;
- регистрацию в `assets`;
- формат GLB или glTF;
- размер;
- структуру файла на уровне выбранного валидатора;
- наличие всех зависимостей glTF;
- отсутствие произвольных внешних ресурсов;
- корректность `controls`;
- корректность `camera`;
- корректность `scale`.

Для GLB предпочтителен самодостаточный файл.

Для glTF все бинарные данные и текстуры должны находиться внутри архива и быть зарегистрированы в `assets`.

Нельзя ограничиваться проверкой расширения файла.

Если модель не удаётся корректно разобрать или проверить, импорт завершается ошибкой.

## 10. Результат проверки

Backend возвращает структурированный результат, содержащий:

- `valid`;
- `errors`;
- `warnings`;
- сведения о статье;
- сведения о блоках;
- сведения о файлах;
- при наличии `technical_knowledge` — сведения о количестве и результатах проверки технических сущностей.

Пример:

```json
{
  "valid": false,
  "errors": [
    {
      "code": "ASSET_NOT_FOUND",
      "file": "media/repair_model.glb",
      "message": "Файл модели отсутствует в архиве"
    }
  ],
  "warnings": []
}
```

Для ошибок технических данных в ответе должны указываться код ошибки и путь к проблемному полю или сущности, например:

```text
technical_knowledge.diagnostics[0].steps[1].transitions[0].next_step_id
```

Конкретная структура ответа должна соответствовать существующим правилам API проекта.

Ошибки должны содержать идентификатор ошибки, путь к файлу или указание на проблемное поле.

## 11. Preview

После успешной проверки автор получает предварительный просмотр статьи.

Preview использует тот же компонент отображения, что и опубликованная статья.

До подтверждения импорта данные могут храниться во временной области.

При отмене временные файлы удаляются.

Preview должен поддерживать все типы блоков версии 1.3.

Объект `technical_knowledge` не отображается как текст или набор блоков статьи. Его наличие не должно изменять обычное отображение статьи.

## 12. Сохранение статьи

После подтверждения импорта Backend:

1. Создаёт запись в `blog_post` либо обновляет существующую в предусмотренном сценарии.
2. Сохраняет полный JSON.
3. Сохраняет версию формата.
4. Загружает все зарегистрированные файлы из `media/` в Dropbox, включая GLB/glTF и другие assets.
5. Заменяет ссылки на `dropbox:{dl_id}` и проверяет доступность файлов через штатный Dropbox endpoint.
6. Проверяет целостность сохранённого содержимого.
7. Устанавливает статус `draft`.

Операция должна обеспечивать согласованность базы данных и Dropbox. При ошибке до фиксации статьи загруженные файлы удаляются через штатный endpoint удаления Dropbox. После фиксации выполняется readback-проверка JSON и всех идентификаторов файлов. Нельзя оставлять статью со ссылками на отсутствующие файлы.

При сохранении версии 1.3 полный объект `technical_knowledge` должен оставаться в JSON без потери известных и неизвестных дополнительных полей.

## 13. API

Все операции реализуются через существующий `script/template/repair_api`.

Названия ниже являются логическими именами операций и должны быть согласованы с действующим механизмом API.

### 13.1. validateBlogImport

Принимает ZIP и выполняет полную проверку без сохранения статьи.

Возвращает результат проверки, ошибки, предупреждения и сведения о структуре.

Для версии 1.3 дополнительно проверяет `technical_knowledge`, если он присутствует.

### 13.2. previewBlogImport

Формирует данные для предварительного просмотра проверенного архива.

Работает с временными файлами до подтверждения импорта.

Отображает обычные блоки статьи. Не выполняет и не интерпретирует диагностические сценарии.

### 13.3. importBlogPost

Подтверждает импорт и сохраняет статью со статусом `draft`.

Разрешён только после успешной проверки.

Сохраняет полный JSON статьи, включая `technical_knowledge`, если он присутствует.

### 13.4. getBlogPost

Возвращает данные одной статьи и ссылки на её медиафайлы.

Для статьи версии 1.3 возвращает полный JSON, включая `technical_knowledge`.

### 13.5. getBlogPosts

Возвращает список статей с поддержкой существующих требований к фильтрации и пагинации.

### 13.6. editBlogPost

Обеспечивает изменение метаданных статьи в рамках существующей модели прав.

Встроенное редактирование содержимого статьи в Repair Wizards не предусматривается.

Изменение содержимого выполняется подготовкой нового ZIP-архива и повторным импортом/заменой содержимого в предусмотренном системой сценарии.

Если существующая реализация `editBlogPost` уже изменяет JSON статьи, разработчик должен проверить её фактическое использование и согласовать изменение поведения отдельно. Нельзя незаметно удалить действующую возможность или изменить её семантику без проверки зависимостей.

### 13.7. deleteBlogPost

Удаляет статью по существующим правилам управления публикациями.

Удаление файлов выполняется с учётом связей и предусмотренных механизмов восстановления.

## 14. Frontend: ArticleRenderer

Для отображения статей создаётся единый компонент `ArticleRenderer`.

Он получает JSON статьи и отображает блоки в порядке массива `blocks`.

Предлагаемая структура:

```text
ArticleRenderer
  ├── HeadingBlock
  ├── ParagraphBlock
  ├── ImageBlock
  ├── GalleryBlock
  ├── VideoBlock
  ├── ListBlock
  ├── QuoteBlock
  ├── CalloutBlock
  ├── StepsBlock
  ├── TableBlock
  ├── CodeBlock
  └── Model3DBlock
```

Один и тот же `ArticleRenderer` используется в Preview и на странице опубликованной статьи.

Не допускается создание двух независимых механизмов отображения.

Объект `technical_knowledge` не является отображаемым блоком и не передаётся компонентам отображения как обычное содержимое.

## 15. Отображение пошаговых инструкций

`StepsBlock` отображает каждый элемент `items` в заданном порядке.

Для каждого шага отображаются:

- номер;
- заголовок;
- текст;
- изображение, если указано;
- предупреждение, если указано.

Изображение должно отображаться непосредственно в соответствующем шаге.

Предупреждение должно быть визуально отделено от обычного текста.

На мобильном устройстве блок должен оставаться читаемым без горизонтальной прокрутки всей страницы.

## 16. Отображение технических таблиц

`TableBlock` отображает:

- строку заголовков;
- строки значений;
- все ячейки в заданном порядке.

Требования:

- корректная ширина колонок;
- читаемость технических значений;
- адаптация к мобильным устройствам;
- горизонтальная прокрутка при необходимости;
- отсутствие выхода таблицы за пределы страницы.

Таблицы не должны терять значения при изменении ширины экрана.

## 17. Отображение кода и команд

`CodeBlock` отображает текст в моноширинном шрифте.

Необходимо предусмотреть:

- сохранение пробелов и переносов строк;
- горизонтальную прокрутку длинных строк;
- подсветку синтаксиса, если доступна для указанного языка;
- кнопку копирования;
- корректное отображение на мобильных устройствах.

Содержимое блока не исполняется.

Подсветка синтаксиса не должна быть обязательным условием отображения.

## 18. Изображения и галереи

Изображения:

- адаптируются к ширине контейнера;
- сохраняют пропорции;
- поддерживают увеличение;
- используют `alt`;
- загружаются с учётом производительности.

Галереи:

- горизонтальная прокрутка;
- свайп на мобильных устройствах;
- стрелки навигации на настольных устройствах;
- увеличение изображения;
- подписи;
- корректное поведение при разном количестве и размерах изображений.

Загрузка изображений выполняется по мере необходимости.

## 19. Видео

Видео отображается через поддерживаемый механизм встраивания или безопасный внешний переход.

Backend проверяет URL по разрешённому списку платформ.

Frontend не вставляет произвольный HTML из JSON.

Для неподдерживаемой платформы выводится сообщение или ссылка на внешний ресурс.

## 20. Отображение 3D-моделей

### 20.1. Просмотрщик

Используется готовый Web 3D-просмотрщик с поддержкой GLB/glTF.

Допускается Google `<model-viewer>` или эквивалентное решение.

Разработка собственного 3D-движка не требуется.

### 20.2. Функции

Просмотрщик должен обеспечивать:

- загрузку модели;
- отображение в отдельной области статьи;
- вращение;
- масштабирование;
- начальный ракурс;
- адаптацию к мобильным устройствам;
- обработку ошибок.

Параметры `controls`, `camera` и `scale` преобразуются в настройки выбранного просмотрщика.

`pan` поддерживается только при наличии такой возможности у выбранного решения.

### 20.3. Производительность

Предусмотреть:

- отложенную загрузку модели;
- загрузку при приближении блока к видимой области;
- индикатор загрузки;
- ограничение размеров области просмотра;
- освобождение ресурсов при удалении компонента;
- обработку ошибок загрузки и декодирования.

3D-модель не должна блокировать отображение текстовой части статьи.

## 21. Совместимость со старыми статьями и версиями формата

Необходимо сохранить отображение ранее созданных статей.

До реализации разработчик определяет фактический формат существующего содержимого.

Требования:

- прежний механизм отображения сохраняется;
- новый `ArticleRenderer` используется для формата 1.2 и 1.3 в пределах поддерживаемой структуры блоков;
- формат определяется по существующим данным;
- автоматическое преобразование старых статей не выполняется без отдельного согласования;
- корректные ZIP-архивы версии 1.2 продолжают приниматься;
- ZIP-архивы версии 1.3 принимаются с объектом `technical_knowledge` или без него;
- отсутствие `technical_knowledge` не является ошибкой;
- объект `technical_knowledge` сохраняется и возвращается API, но не отображается как содержимое статьи;
- неизвестные дополнительные поля сохраняются;
- неизвестные типы блоков отклоняются.

## 22. Безопасность

Необходимо учитывать:

- ZIP Slip;
- подмену MIME-типа;
- вредоносные файлы;
- чрезмерный размер распакованных данных;
- некорректные пути;
- произвольные внешние URL;
- HTML и JavaScript в содержимом;
- внешние ресурсы 3D-моделей;
- чрезмерную нагрузку на браузер;
- чрезмерную вложенность и объём структурированных технических данных.

Все пользовательские данные проверяются на Backend.

Frontend не заменяет серверную валидацию.

Код из блока `code` никогда не исполняется.

Диагностические переходы из `technical_knowledge` обрабатываются как данные. Backend не выполняет переданные выражения, функции или скрипты.

3D-просмотрщик работает в безопасном режиме и не выполняет произвольный код из файлов модели.

## 23. Лимиты

Используются ограничения Приложения № 1:

| Параметр | Ограничение |
|---|---:|
| Максимальный размер ZIP | 100 MB |
| Максимальный размер изображения | 10 MB |
| Максимальный размер одной 3D-модели | 30 MB |
| Максимальный суммарный размер модели glTF с зависимостями | 30 MB |
| Максимальное количество блоков в `blocks` | 200 |
| Минимальное количество изображений в галерее | 2 |
| Максимальная глубина каталогов | 2 |

Количество элементов `technical_knowledge` не входит в лимит блоков `blocks`.

Для структурированных технических данных должны быть предусмотрены отдельные ограничения по количеству сущностей, размеру JSON и глубине вложенности. Конкретные значения фиксируются в реализации Backend и должны быть согласованы с Приложением № 1 до ввода импорта версии 1.3 в эксплуатацию.

При выявлении ограничений хостинга, PHP или браузеров разработчик фиксирует их и предлагает согласованное изменение лимитов.

Разные лимиты на уровне спецификации и Backend без согласования не допускаются.

## 24. Этапы реализации

### Этап 1. Импорт и базовое мультимедийное отображение

- приём ZIP;
- проверка JSON версии 1.2 и 1.3 для базовых полей;
- проверка `assets`;
- сохранение JSON и файлов;
- Preview;
- текстовые блоки;
- изображения;
- галереи;
- видео;
- списки;
- цитаты;
- информационные блоки.

### Этап 2. Ремонтные блоки

- пошаговые инструкции `steps`;
- технические таблицы `table`;
- отображение команд и кода `code`;
- адаптация этих блоков к мобильным устройствам.

Этап 2 входит в первую поставку функциональности статей.

### Этап 3. Базовая поддержка 3D

- импорт GLB/glTF;
- проверка зависимостей;
- сохранение моделей;
- отображение через готовый просмотрщик;
- вращение;
- масштабирование;
- начальный ракурс;
- адаптивность;
- обработка ошибок.

Этап 3 также входит в первую поставку функциональности статей.

### Этап 4. Приём и хранение структурированных технических данных

- приём необязательного `technical_knowledge`;
- проверка структуры известных сущностей;
- проверка идентификаторов и межсущностных связей;
- проверка переходов между диагностическими шагами;
- проверка ссылок на `assets`;
- проверка допустимых значений перечислений;
- сохранение полного JSON без потери неизвестных дополнительных полей;
- возврат полного JSON через API;
- сохранение совместимости с версией 1.2;
- отсутствие влияния `technical_knowledge` на обычное отображение статьи.

Этап 4 не включает запуск диагностических процедур или пользовательский интерфейс их прохождения.

### Этап 5. Расширенные интерактивные материалы

Отдельная будущая задача:

- разнесённые модели;
- интерактивные технические схемы;
- специализированные CAD-просмотрщики;
- внешние просмотрщики;
- AR/VR;
- дополнительные интерактивные блоки.

## 25. Критерии приёмки

Реализация считается выполненной, если:

1. Используются существующие `blog_post` и `blog_topic` без дублирующих сущностей.
2. Импорт выполняется через существующий `repair_api`.
3. Система принимает ZIP формата 1.2 и 1.3.
4. Проверяется структура JSON и `assets`.
5. Проверяется соответствие ссылок фактическим файлам.
6. Статья сохраняется со статусом `draft`.
7. Файлы размещаются в отдельном каталоге статьи.
8. Preview отображает все поддерживаемые блоки.
9. Опубликованная статья использует тот же механизм отображения.
10. Галереи поддерживают прокрутку и мобильный свайп.
11. Видеоссылки проверяются.
12. Пошаговые инструкции отображаются с фотографиями и предупреждениями.
13. Технические таблицы корректно отображаются на мобильных устройствах.
14. Код и команды отображаются с сохранением форматирования и возможностью копирования.
15. GLB-модель успешно импортируется и отображается.
16. glTF-модель импортируется со всеми зависимостями.
17. Некорректный импорт не оставляет частично сохранённую статью.
18. Сохранена совместимость со старыми статьями.
19. Произвольный HTML и JavaScript не исполняются.
20. Импорт и отображение соответствуют требованиям безопасности и производительности.
21. Корректные архивы версии 1.2 продолжают приниматься.
22. Корректный архив версии 1.3 без `technical_knowledge` принимается.
23. Корректный архив версии 1.3 с `technical_knowledge` принимается.
24. Проверяются ссылки между техническими сущностями.
25. Проверяются переходы между диагностическими шагами.
26. Проверяются ссылки технических сущностей на `assets`.
27. Структурированные технические данные сохраняются без потери.
28. Неизвестные дополнительные поля в технических данных сохраняются.
29. `ArticleRenderer` отображает обычные блоки и не выводит `technical_knowledge` как текст статьи.
30. API возвращает полный объект `technical_knowledge` для статьи версии 1.3.

## 26. Что не входит в объём работ

Не требуется:

- отдельная CMS;
- встроенный редактор статей;
- интеграция с API конкретного ИИ;
- собственный генератор статей;
- собственный 3D-движок;
- выполнение команд из статей;
- CAD-редактор;
- AR/VR;
- интерактивные электрические схемы;
- массовое преобразование старых статей;
- изменение архитектуры заказов, чатов и других подсистем;
- выполнение диагностических сценариев;
- формирование диагностических брифов;
- интерпретация ответов заказчика;
- автоматическое формирование технического задания;
- автоматическое создание заказа;
- каталог и аренда диагностических инструментов.

---

**Итог:** Repair Wizards принимает универсальный пакет статьи, проверяет его, сохраняет в существующей архитектуре и отображает через единый механизм. Формат 1.3 дополнительно позволяет передавать и хранить структурированные технические знания для будущего использования ИИ, не создавая отдельную CMS, редактор или диагностическую подсистему.
