## Обнаруженные дефекты

### BUG-ART-COM-001 — UI запрещает отвечать на удалённый комментарий

- Приоритет: средний
- Файл: `src/app/components/Article/ArticleComment.jsx`
- Место: условие отображения кнопки «Ответить» (около строки 194).
- Наблюдение: кнопка выводится только при `!comment.deleted && canReply`.
- Проблема: мягкое удаление комментария не должно закрывать ветку обсуждения. Backend сохраняет строку комментария и допускает ответ с таким `parent_id`, но интерфейс скрывает действие.
- Ожидаемое поведение: разрешить ответ на удалённый комментарий, сохраняя визуальное обозначение «Комментарий удалён».
- Проверка после исправления: открыть статью, удалить свой последний комментарий, затем под ним добавить ответ; ответ должен сохраниться и отображаться вложенно.

### BUG-ART-COM-002 — локальный режим допускает родителя из другой статьи

- Приоритет: средний (затрагивает целостность тестовых данных)
- Файл: `src/app/state/api/localComments.ts`
- Место: проверка родителя около строки 116.
- Наблюдение: код проверяет только наличие комментария с указанным ID в общем массиве. После этого новый комментарий создаётся с `article_id: params.articleId`.
- Проблема: не проверяется, что `parent.article_id === params.articleId`. Поэтому можно создать ответ в статье A, указав родителя из статьи B.
- Ожидаемое поведение: отклонять такой запрос до создания записи; проверять существование родителя и совпадение `article_id`.
- Проверка после исправления: создать комментарий в статье A и попытаться ответить на него при передаче articleId статьи B; операция должна завершиться ошибкой, состояние не должно измениться.

## Замечания, требующие уточнения или отдельной проверки

### NOTE-ART-COM-003 — флаг гостевого режима frontend/backend может расходиться

- Frontend: `src/app/components/Article/ArticleComments.jsx` разрешает взаимодействие по `CONFIG.BLOG?.allowGuestTesting`.
- В проверенном `script_templates/repair_api_test_page.php` флага `$blog_guest_testing` нет; `addBlogPost` требует авторизованный `u_id > 0`. Следовательно, гостевая отправка комментария через этот шаблон запрещена независимо от frontend-флага.
- Риск: если frontend-конфигурация включит гостевой режим, UI покажет форму, но backend отклонит запись как Unauthorized.
- Статус: условное замечание. Проверить конфигурацию окружения и принять одно согласованное решение; не включать гостевой режим без отдельного согласования.

### NOTE-ART-COM-004 — локальные комментарии не являются общими для пользователей

- Файл: `src/app/state/api/localComments.ts`.
- Наблюдение: локальный адаптер хранит состояние в браузере (localStorage).
- Следствие: комментарии локального режима не синхронизируются между пользователями/устройствами. Это допустимо только как изолированный демонстрационный или тестовый режим, не как рабочий backend.
- Статус: ограничение режима, не дефект при условии, что локальный режим используется только для тестирования.

## Дополнительные замечания статического анализа

### NOTE-ART-COM-005 — локальный адаптер не повторяет серверное ограничение длины

Файл: `src/app/state/api/localComments.ts`.

UI-компонент `CommentForm` считает Unicode-символы и блокирует отправку текста длиннее 1000 символов. Backend также проверяет длину. Однако сами функции `addLocalBlogPost` и `editLocalBlogPost` не проверяют предел 1000 символов. При прямом вызове адаптера в обход UI локальный режим принимает текст, который сервер отклонит.

Статус: низкий приоритет / защита контракта. Проверить, что локальный адаптер должен гарантировать те же ограничения независимо от UI; автоматического теста на этот случай в текущем наборе не обнаружено.

### NOTE-ART-COM-006 — потенциальная взаимная блокировка при одновременном ответе и удалении корневого комментария

Файл: `script_templates/repair_api_test_page.php`, действия `addBlogPost` и `deleteBlogPost`, helper `$blog_lock_comment`.

- Добавление ответа сначала блокирует родительский комментарий через `SELECT ... FOR UPDATE`, а затем вставляет строку, ссылающуюся внешним ключом на статью.
- Удаление корневого комментария сначала блокирует строку статьи через `SELECT ... FOR UPDATE`, затем блокирует сам корневой комментарий.
- При одновременном ответе на корневой комментарий и его удалении возможен обратный порядок блокировок: транзакция ответа держит комментарий и ожидает shared-lock строки статьи для проверки FK; транзакция удаления держит статью и ожидает комментарий.

InnoDB может разрешить такой цикл обнаружением deadlock и откатом одной транзакции. Это не доказывает потерю данных, но одна операция может завершиться ошибкой при реальной гонке; приложение не выполняет явный retry deadlock-транзакции.

Статус: потенциальный concurrency-риск, runtime не подтверждён. Требуется отдельный тест с двумя параллельными соединениями на изолированной тестовой статье. Не объявлять подтверждённым дефектом до воспроизведения.

До любых записей в рабочую БД необходимо выбрать и реализовать отдельный закрытый QA-механизм. Предпочтительный вариант — отдельный backend QA endpoint/action, выключенный по умолчанию и доступный только при явном серверном feature flag и отдельном секретном токене. Он должен:

- работать только с явно помеченными QA-записями;
- создавать тестовую статью со статусом `draft` и проверять фактический статус после INSERT;

- выполнять CRUD комментариев с отдельным QA-контекстом;
- сохранять точные созданные ID и идентификатор запуска;
- выполнять cleanup только по точным ID текущего запуска и только после повторной проверки маркеров/владельца;
- завершаться без изменений, если схема, feature flag, права или условия cleanup не совпадают с ожидаемыми.

Перед реализацией endpoint необходимо проверить фактическую схему `blog_post`, способ управления шаблонами на сервере и доступный механизм серверных секретов. До этого ограничиваемся read-only проверками и тестами локального адаптера. На production не выполнять пробные INSERT/UPDATE/DELETE.

В шаблоне определяется колонка статуса по фактической схеме `blog_post`. Для `is_published`/`published` используется значение 1; для строкового `status`/`blog_status` — `published`. Оговорка: если в таблице нет распознанной колонки статуса, `$blog_public_where` остаётся пустым. Поэтому безопасность публичной фильтрации зависит от фактической схемы и наличия миграции публикации; это следует проверять по схеме, а не считать безусловно гарантированным только по коду.

Миграция `sql/blog_article_publication.sql` добавляет строковый `status` с `DEFAULT 'published'`. Следовательно, обычный INSERT без явного статуса способен создать публичную статью. Не использовать такой INSERT для QA.
